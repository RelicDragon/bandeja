# Booking

`ClubIntegrationType` (`schema.prisma` + `@shared/clubIntegration`): `BOOKTIME` | `PADELOO` | `KLIKTEREN` | `NSPADELSUPABASE` | `WELTNER`.

FE owns snapshot refresh. BE merges occupancy: app games + admin holds + external busy (`CourtOccupancyService.getOccupancy`). Freshness: `BOOKTIME_SNAPSHOT_FRESH_MS` = 60s (`@shared/gameBooking/booktimeSnapshotFreshness`) — used for Booktime/Padeloo/Klikteren snapshot staleness.

Occupancy merge `queryExternalBlocks` loads snapshots for BOOKTIME, PADELOO, KLIKTEREN only. NSPADELSUPABASE availability is the Nspadel adapter + `/nspadel/*`, not that merge path.

### Read-only occupancy surfaces

Two surfaces read occupancy without booking anything, and both inherit those constraints unchanged:

- **The public club page's "Today at a glance" strip** (`GET /clubs/:id/today-availability`, [club-admin.md](./club-admin.md)). Our own database only. Klikteren is proxy-only and no provider URL — least of all a club's Supabase URL — may reach the browser, so the response is hour buckets plus one timestamp and nothing else. Only **hard** blocks paint a court grey (`isOccupancyHardBlock`: a club booking or a hold); a game without a booked court is a soft block and leaves the hour green, because the court is still bookable. Hour buckets are built one `fromZonedTime` call per hour in the **club's** city timezone (`buildHourBuckets`), so a DST transition inside the day does not shear the strip. The window comes from the flat `Club.openingTime` / `closingTime` strings; a club that closes after midnight is rendered to end of day rather than wrapping. The strip is decoration: fetched only when `booking.available` is true, never blocking first paint, and a failure simply means no strip.
- **`GET /games/:id/indoor-alternatives`**, the move-indoor sheet ([weather.md](./weather.md)). A court is busy when an overlapping block is a hard block or another app game; the game's **own** blocks are ignored. It reports exactly what the club schedule grid reports.

## Game ↔ booking

`GameExternalBooking` + `@shared/gameBooking` (`evaluateLinkedBookingCoverage`, `computeGameBookingStatus`, `linkBookingToGame`, `parseCreateGameDeepLinkSearch`). Coverage: court count + time window vs game start/end. Shared reservation across games is informational.

**Read-side display** (card, game info, Court(s) card, organizer next steps) goes through one FE adapter, `Frontend/src/utils/courtReservationView.ts` (`deriveCourtReservations` + `reservationCopy`): slot *Not booked yet* / *Booked by organizer* / *Booked · <provider>*; summary *Not booked yet* / *k of N booked* / *All courts booked* / *Booked, gap at HH:MM* / *Booked by organizer* (every held slot is only `REPORTED`, `isReservedByReportOnly`). **Organizer's word vs club booking:** `REPORTED` (nothing in the club's system proves it) is sky with a person-check icon (`ReservationPillTone` `reported`), never green; green is for linked bookings only. Display code never reads `hasBookedCourt` / `bookingStatus` directly; the adapter falls back to them for payloads without the court-slot fields, and Find cards (no `linkedBookings`) take `EXTERNAL_FULL` as all booked and `EXTERNAL_PARTIAL` as a count-less *Partly reserved* (`games.reservationPartly`). Game cards show the summary only when something is held (never *Not booked yet*). The chat `GAME_BOOKING_STATUS_CHANGED` line still renders the legacy enum in the older words (chat namespace, not yet renamed).

### Linked-games lookup is viewer-scoped

`GET /{booktime,padeloo,klikteren,nspadel}/linked-games/:externalBookingId` and `POST /booktime/linked-games/batch` (`booktimeGameLink.service.ts`) answer "which games use this provider booking?". Provider booking ids are guessable, so the answer only ever contains games the **caller** may see:

- games where the caller is on the roster (`PLAYING` / `NON_PLAYING` / `IN_QUEUE`, any role — the same statuses `hasParentGamePermission` uses); `INVITED` does not count;
- games whose **parent** the caller runs as OWNER/ADMIN (league fixtures, matching `canEditGame`);
- everything for global admins.

Anyone else gets `[]` (batch: every requested id present with `[]`). The response shape is unchanged, so shipped apps keep working — they just see a subset. Consequences: the "N other games share this reservation" hint and the cancel-booking auto-unlink (`unlinkBookingFromLinkedGames`) only cover games the caller is on; another organizer's game sharing the booking keeps its link until they remove it. Tests: `npm --prefix Backend run test:booktime-linked-games`. Delete game does not cancel club bookings. Booking on create is all-or-nothing where the provider can cancel (Booktime, Padeloo, Klikteren): a partial multi-court booking or a failed game create cancels what was booked. NS Padel and Weltner cannot cancel in the app: booked courts stay booked and are shown; Weltner preserves the receipt and retries game saving.

Create/edit booking flow: `supportsClubBookingFlow` — create GAME/TRAINING/TOURNAMENT; edit those + LEAGUE (on an existing game, reservations are made from the Courts card, not the edit drawer). EVENT cannot book/link (`eventCreateDefaults.applyEventUpdateInvariants`).

Create ("At the club?": Reserve now / Already reserved / Not yet, court slots, occupancy-aware times, rollback on partial failure): [create.md](./create.md#courts-and-reservations-on-create).

### `?date=` on `/create-game`

`parseCreateGameDeepLinkSearch` also parses `?date=yyyy-MM-dd`, used by the club page's court chips (`/create-game?clubId=&courtId=&date=`).

- The value must be a real calendar date; a malformed or impossible one is dropped rather than passed through, so the wizard never seeds an `Invalid Date`.
- `createGameDataFromDeepLinkSearch` turns it into `startTime` at **local noon**, the same convention `headerStore.setCreateGameInitialDate` already uses. That pins the wizard's date without pretending a slot was picked.
- An explicit `startTime` always wins; `date` is ignored when both are present.

### Court slots

A game's courts are its **slots** (`GameCourt`, ordered). Each slot is reserved when the organizer **reported** it (`reservation = REPORTED`, stamped `reportedById` / `reportedAt`) or when a linked booking sits on it (`GameExternalBooking.gameCourtId`). `Game.reportedAnyCourtCount` counts courts reported without naming them. `Game.courtSlotCount` (nullable) is how many courts the organizer chose — the organizer, not the roster, decides (an 8-player americano on one court is one slot). `Game.courtId` always follows the first slot, and a game with a `courtId` always has a slot for it.

- **`PUT /games/:id/court-slots`** (owner/admin, same as editing courts): `{ slots: [{ courtId, reservation: 'NONE'|'REPORTED' }], reportedAnyCourtCount, courtSlotCount? }` — authoritative order, courts and reports; `courtSlotCount` absent = unchanged, `null` = clear (default rule), 1..16 = set. Courts must be the game's club, unique, ≤ 16, sport-compatible; a slot with a linked booking cannot be dropped (unlink first). Never moves the time. **Roster cap:** never more courts than the roster needs (`defaultCourtSlotCount`: `ceil(maxParticipants / 4)`, `/ 2` for singles — a 4-player 2v2 has one court). A request whose courts or `courtSlotCount` exceed max(need, the game's current courts, its stored `courtSlotCount`) → 400; a game already above the cap (older data) keeps its courts and may only shrink. Every UI stepper (create, edit drawer, Courts card) uses the same cap; in the edit drawer a full court set swaps the last unlinked court instead of adding one. Responds with the slot view: `gameCourts` (with reservation fields), `linkedBookings` (with `gameCourtId`), `reportedAnyCourtCount`, `courtSlotCount`, `hasBookedCourt`, `bookingStatus`. Game payloads carry `courtSlotCount` too (additive).
- **Placement.** `POST /games/:id/link-booking` accepts optional `gameCourtId` (must be the game's and match the booking's court). Without it the booking goes on its court's slot; a court the game lacks gets a slot appended. Snapshot refreshes re-place the same way. `POST /game-courts/game/:id` (old apps) keeps rows — and reservations and links — of courts that stay; a booking whose court was removed stays linked but unplaced. A court added by an old app starts REPORTED only when the game was "booked" by report alone and every slot was REPORTED.
- **`?timePolicy=explicit`** on link / `PATCH /games/:id/bookings` / snapshots / `PUT /games/:id`: booking writes never derive or move the game's time for that request (as if `timeOverride`). Absent → old behaviour (bookings drive the time unless `timeOverride`).
- **Legacy fields.** `bookingStatus` / `hasBookedCourt` are derived on every booking sync by the shared core `deriveCourtReservations` (`@bandeja/shared/gameBooking/courtReservations`; backend adapter `computeLegacyBookingFieldsFromSlots`). N slots: `courtSlotCount` set → max(courtSlotCount, assigned courts); unset (every pre-existing game) → assigned courts when any, else the roster need (`computeBookingSelectionLimits(...).min`), at least 1. The UI prefills a new choice with `defaultCourtSlotCount` (the roster need). Links matching no assigned court fill implicit "any court" slots, `reportedAnyCourtCount` fills only those. With links → `EXTERNAL_FULL` iff every slot is reserved and no linked slot has a gap (unknown booking times count as a gap; `timeIsSet = false` skips coverage), else `EXTERNAL_PARTIAL`; otherwise `MANUAL` iff a slot is reported, else `NONE`. `hasBookedCourt` = anything reserved, and always true while any link exists (old apps). Differences from the earlier backend-only rule (8 players + 1 linked court stays FULL, as before): a link beyond N reserves nothing, `reportedAnyCourtCount` beyond the implicit slots is ignored. The booking-status chat notice posts only when the value changes, including after court-set edits.
- **Occupancy.** `CourtOccupancyService` emits one app-game block **per court slot** (player and admin views; a `courtId` filter matches any slot). Each game block carries additive `gameId` and `reservation: 'planned' | 'reserved'` (slot REPORTED or linked); `hasBookedCourt` keeps its game-level meaning for shipped apps. Soft / hard (`isOccupancySoftBlock`, agent `isSlotHardBlock`) are per slot. `GET /games/booked-courts` slots carry `gameId` / `reservation` too.
- **Old-app `hasBookedCourt`.** `true` on a game with nothing reserved and no links → every slot REPORTED (or `reportedAnyCourtCount = 1` without slots); re-sending it is a no-op. `false` → clears every report; still refused while links exist. A `PUT /games/:id` that only moves `courtId` moves a single unlinked slot with it.

Tests: `npm --prefix Backend run test:court-slots`, `npm --prefix Backend run test:reservation-changes`.

### Clash guard

New clients only (`?timePolicy=explicit`): `PUT /games/:id` (window moved → every slot; only the primary court moved → that court) and `PUT /games/:id/court-slots` (courts added by the request) answer **409** `{ code: 'court.clash', details: [{ courtId, start, end, kind, gameId? }] }` and write nothing. `kind`: `club` (club-system busy block), `hold` (club-admin hold), `app_game_reserved` (another app game whose slot on that court is reserved; `gameId` given). Checked per slot over the part of the window the game has not reserved itself: a planned slot — the whole window; a linked slot — its gaps (its own bookings show as club-busy); a REPORTED slot — exempt (the organizer's phone booking shows as club-busy; the planner says "tell the club"). Planned app games and games sharing one of this game's bookings never clash. Without the policy nothing changes. Code: `Backend/src/services/gameCourt/courtClash.service.ts`.

### Game only (legacy)

No screen sets it any more (2026-10): the game page reads a `GAME_ONLY` game like any other (see "Court states") and the editor saves it back as `CLUB`. Server behaviour, unchanged for store builds:


`Game.courtBookingMode`: `CLUB` (default) | `GAME_ONLY`. "Game only" = the organizer handles the court themselves: the clash guard never checks the game, so it is never blocked by the club's schedule. `POST /games` and `PUT /games/:id` accept optional `courtBookingMode` (anything else → 400; omitted = `CLUB` on create, unchanged on update — store builds never send it). Every game payload (detail, lists, Find cards, sockets) and the court-slot view carry it. **Links win:** `syncGameBookingState` flips a `GAME_ONLY` game with ≥ 1 linked booking back to `CLUB` in the same transaction, so link-booking, create with `externalBookingIds`, snapshot writes and the reschedule journal all end as `CLUB`. Setting `GAME_ONLY` while links exist → 400 `gameDetails.courts.gameOnlyHasLinks` (unlink first). Switching back to `CLUB` with `?timePolicy=explicit` runs the clash guard on every slot (409 `court.clash` → the client shows "This court is taken at the club" with **Keep Game only** as the main action; only the secondary "I booked it myself" marks the courts REPORTED and retries). `bookingStatus` / `hasBookedCourt` derivation is unchanged. Code: `Backend/src/services/game/courtBookingMode.ts`; test: `courtBookingMode.integration.test.ts` (in `test:court-slots`).

### Club-side drift

`GameExternalBooking.upstreamState` (`OK` | `MOVED` | `MISSING` | `UNKNOWN`), `upstreamStart` / `upstreamEnd` (provider times when MOVED), `upstreamCheckedAt`; serialized on `linkedBookings` (additive). The backend never asks the provider; the app tells it:

- **Mirror sync** (`PUT /bookings/mirror`): for every link of an ANNOUNCED/STARTED game of that club booked by the syncing user (`bookedByUserId`) with the same provider + `externalBookingId`: different times → `MOVED`; listed CANCELLED, or absent from a `complete` list whose range holds the link's start → `MISSING`; same → `OK`. Links outside the range, or absent from an incomplete list, are left alone. Games whose drift changed get `game-updated`.
- **`POST /games/:id/bookings/:linkId/upstream-check`** (owner/admin) `{ present: boolean, start?, end? }` → the serialized link. Absent → MISSING; present with other times → MOVED; else OK.
- A snapshot refresh (`PUT /games/:id/booking-snapshots`) resets the link to OK.

Nothing moves on its own. **`POST /games/:id/bookings/:linkId/accept-upstream`** (owner/admin) `{ mode: 'move_game' | 'keep_game', startTime?, endTime? }`, MOVED links only (else 409 `booking.upstream.notMoved`, also when a newer observation raced it): both modes set the link to the provider's times (→ OK). `keep_game`: game time stays, coverage recomputed (status notice if it changed). `move_game`: the game moves (given window, default: each edge shifts like the booking's) through `GameUpdateService.updateGame` with the link write in the same transaction — one time-change notice, attendance reset, clash guard. Response `{ mode, startTime, endTime, bookingStatus, hasBookedCourt, linkedBookings }`.

### Reschedule journal

The client plans (`planReschedule`) and runs provider steps itself; the server keeps the run (`GameReservationChange` + steps) so another device can resume. Owner/admin only.

- **`POST /games/:id/reservation-changes`** `{ plan: { steps: [{ idempotencyKey, kind, … }] , … }, fromStart, fromEnd, toStart, toEnd }` → 201 `{ data: change, resumed: false, abandonedId }`. One RUNNING run per game: another fresh one → 409 `reservationChange.running` with `active`; the same run re-posted by its creator (same target window and step keys) → 200 `resumed: true`; a RUNNING run untouched for 15 min is stale → ABANDONED and replaced (`abandonedId`). ≤ 200 steps, ≤ 1 `save_game`.
- **`GET /games/:id/reservation-changes/active`** → change (with `stale`) or `null`.
- **`PATCH /reservation-changes/:id/steps/:idempotencyKey`** `{ status, result?, error? }` → change. Monotonic: PENDING → any; RUNNING → DONE/FAILED/SKIPPED/NEEDS_CLUB; FAILED → RUNNING/DONE/SKIPPED/NEEDS_CLUB (retry); NEEDS_CLUB → DONE/SKIPPED; DONE/SKIPPED final. The same status again is a no-op (keeps the stored result). Else 409 `reservationChange.stepTransition`. A finished run only accepts NEEDS_CLUB → DONE/SKIPPED. `save_game` cannot be set DONE here (400 `reservationChange.saveGameServerOnly`). Every patch refreshes the run's `updatedAt`.
- **`POST /reservation-changes/:id/save-game`** `{ startTime, endTime, slotUpdates?, linksToAdd?, linksToRemove? }`: one transaction through `GameUpdateService.updateGame` (`timePolicy=explicit`): time (one notice, attendance reset), links removed (link id or `externalBookingId`), `slotUpdates` (the `PUT court-slots` body), links added (`link-booking` bodies without `gamePatch`; an already linked booking is only re-placed), clash guard, step DONE with `result { startTime, endTime, addedLinkIds, removedLinks }`. Any failure rolls back everything and marks the step FAILED. A retry after DONE → `{ replayed: true, result, change }`, nothing written. Response `{ replayed, result, change, linkedBookings }`.
- **`POST /reservation-changes/:id/finish`** `{ state: COMPLETED | FAILED | ROLLED_BACK | ABANDONED }`: from RUNNING only; the same state again is a no-op; COMPLETED needs no PENDING/RUNNING step (409 `reservationChange.stepsOpen`).
- **Follow-ups.** NEEDS_CLUB steps of any run are listed on `GET /games/:id` for organizers as `pendingClubFollowUps: [{ changeId, changeState, idempotencyKey, kind, error, updatedAt, step }]` (`step` = the plan step); absent when none or for anyone else; never broadcast.
- **Client runner** (`Frontend/src/features/court-reservations/reservationRunner.ts`). Creates the server run before any step. A 409 `reservationChange.running` stops the run before anything happens — no booking, and no fallback to separate non-atomic calls; the sheet says "Another change is in progress" and offers **Finish it** (the active run is the user's own: it is rebuilt from `active` and resumed) or asks to wait (someone else's; a stale run is taken over by the server on the next try). Any other create failure (offline) still runs, saving through the separate calls.
- **Planner court choice.** When a court clashes, `planReschedule` switches to the first alternative court with nothing on it at the new time, and only then to one where a planned app game would merely overlap.

Change payload: `{ id, gameId, createdById, state, stale, plan, fromStart, fromEnd, toStart, toEnd, createdAt, updatedAt, steps: [{ id, idempotencyKey, kind, status, result, error, updatedAt }] }` (steps in plan order). Code: `Backend/src/services/gameReservationChange/`.

## Weltner: saved phone and guest reservations

`WELTNER` connects a player's phone number separately for each club. This is a booking contact, not a verified phone or a Weltner login/token. Bandeja authentication is required to save/change/disconnect it and to submit or read reservations. The backend supplies the authenticated player's profile name. Phone numbers must include a country code.

- Fixed upstream: `https://booking.weltner.site`; the frontend only calls `/api/weltner/*`.
- Admin selects `WELTNER`; `integrationConfig` is null. Map each court's `externalCourtId` to its actual Weltner slug. X-Padel Niš: Yucatán → `teren-1-yucatan`, Azteca → `teren-2-azteca`. Club city timezone: `Europe/Belgrade`. Do not match these to another club by name alone.
- Availability is exact `{start,end,duration}` tuples, with durations 60/90/120/180 minutes and an inclusive today-to-30-days horizon. Never infer physical busy ranges by inverting duration-specific availability. Weltner is not part of `queryExternalBlocks`; the local Today strip cannot establish upstream availability. The booking backend rechecks the exact tuple before submission.
- `POST /api/weltner/clubs/:clubId/bookings` resolves the mapped court and saved contact, then submits `{court,date,start,duration,name,phone}` once. `duration` is a string upstream. Midnight ends carry over to the next calendar day in the receipt.
- `WeltnerBooking` records SUBMITTING/CONFIRMED/REJECTED/UNKNOWN. The unique user/club/court/date/start/duration key reuses a confirmed receipt after a failed game save. Uncertain attempts block resubmission. There is no automatic rollback or automatic POST retry. A partial multi-court success stays booked and is shown to the player.
- `weltner:<id>` is a local receipt ID, never an invented provider reference. A provider ID is retained separately only when returned. Game links require a confirmed receipt belonging to the acting player and the game's club; snapshot court/times come from the stored receipt.
- Confirmed receipts participate in the shared My-tab, club, upcoming/past settings, and existing-reservation lists. Settings separately shows uncertain outcomes and preserves receipts after disconnect. All lists show only bookings submitted through Bandeja.
