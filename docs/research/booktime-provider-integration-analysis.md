# Booktime integration as a reference for Weltner

Research date: 2026-09-20. Scope: current working-tree source, including existing uncommitted work. No application code changed, no bookings created or cancelled, no tests run. This file analyses Bandeja; the separate Weltner investigation establishes the target's public API. Source references are repository-relative with observed line numbers; these can shift as the working tree changes.

## Main conclusion

Reuse the club/court selection, timezone conversion, game-link coverage, and availability UI. The user subsequently requested Booktime-style authentication: preserve the connection UX requirement, while distinguishing a Bandeja-managed booking profile from real upstream authentication. The public Weltner guest client does not establish an upstream login contract; see the authentication section in [the Weltner analysis](weltner-xpadel-integration-analysis.md). Nspadel is the closer existing example of booking with the player's contact details, but it has limitations that should not become Weltner's contract. The provider interface currently assumes every provider can create a confirmed reservation, list bookings, and cancel. Capability differences and uncertain outcomes need explicit representation before full parity can be claimed. Sources: `Frontend/src/integrations/booking/ClubBookingProvider.ts:23`, `Frontend/shared/booking/types.ts:20`, `Frontend/src/integrations/booking/providers/NspadelClubBookingProvider.ts:23`.

### Authentication and privacy

Booktime tokens live in browser `sessionStorage`, with in-memory clients, deduplicated hydration, proactive refresh and delayed backend token synchronization. The backend encrypts tokens and stores one auth row per user/club, then decrypts them for that user's session retrieval. It is not a backend Booktime booking client: a dedicated test forbids Booktime HTTP from backend services. Sources: `Frontend/src/integrations/booktime/session.ts:35–99,253–327`; `Frontend/src/integrations/booktime/client.ts:217–315`; `Backend/src/services/booktime/booktimeAuth.service.ts:87–149`; `Backend/src/services/booktime/booktimeNoOutboundHttp.test.ts:24–43`.

Disconnect deletes the backend auth row, then clears proactive refresh, rate-limit state, browser session, memory client and external-booking cache. Unrecoverable-session handling also cancels a pending token-sync timer. The ordinary disconnect path does not visibly cancel that timer; any new implementation should test disconnect racing an in-flight/delayed refresh and should not recreate a deleted connection. No-account Weltner should not create fake credential records or use the existing scout-token mechanism. Sources: `Frontend/src/integrations/booktime/session.ts:60–69,110–128,375–393`; `Backend/src/services/booktime/booktimeAuth.service.ts:145–155`.

For a backend Weltner booking route, derive identity from the authenticated Bandeja user and validate contact details before sending them to the club. Show the actual recipient/contact disclosure in confirmation. Keep secrets and admin credentials outside the browser; the public customer booking contract does not require admin access. This is a recommendation, borrowing the existing profile-contact boundary at `Backend/src/services/nspadel/nspadelBookings.service.ts:319–350`.

### Snapshots and caches

Booktime snapshot refresh is frontend-owned: read saved club-day snapshot, skip if fresh, fetch upstream availability, then save mapped courts. Staleness is 60 seconds. Backend replacement resolves courts, rate-limits writes and takes a PostgreSQL advisory transaction lock for the club/day before deleting/replacing rows. Occupancy merges app games, holds and supported external snapshots. Sources: `Frontend/src/hooks/useBooktimeSnapshotRefresh.ts:39–95`; `Frontend/shared/gameBooking/booktimeSnapshotFreshness.ts:2`; `Backend/src/services/booktime/booktimeSnapshot.service.ts:118–186`; `Backend/src/services/game/courtOccupancy.service.ts:188–227`.

Important gap: that occupancy merge explicitly recognizes only Booktime, Padeloo and Klikteren. Nspadel availability uses its own adapter route. Adding a provider enum/factory does not automatically update the backend schedule, public availability or indoor alternatives. A Weltner implementation must deliberately wire the intended read surfaces. Source: `Backend/src/services/game/courtOccupancy.service.ts:196–198`; `docs/domains/booking.md`.

Upcoming Booktime reservations have a separate five-minute aggregate/company cache persisted with `idb-keyval`; identity-change invalidation clears the loader/hook caches. Provider responses and availability caches serve different purposes. A new cache should key by provider, club, external account where relevant, date and duration, and clear personal data on logout/disconnect. Sources: `Frontend/src/integrations/booktime/booktimeAllUpcomingLoader.ts:20–24,105–107,172`; `Frontend/src/integrations/booktime/booktimeAllUpcomingCacheStorage.ts:1–47`; `Frontend/src/integrations/booktime/booktimeAllUpcomingCacheInvalidation.ts:11–16`.

Do not convert the union of duration-specific valid reservation options into unrestricted free intervals. An allowed 90-minute option is not proof that arbitrary starts or 60-minute reservations within its span are allowed. Missing data or a failed fetch must remain “unknown”, not an empty busy list implying availability. This recommendation follows the difference between `BusySnapshotCourt.busySlots` and explicit bookable options (`Frontend/shared/booking/types.ts:1–18`).

### Time, identity, and reconciliation

Booktime wire times are normalized using the club timezone, and return values are converted to UTC before storage. Date keys use the club timezone. Reuse the general principle, not Booktime-specific compatibility rules for its wire format. Test Belgrade DST transitions, a device outside Serbia, day boundaries and midnight-end slots. Sources: `Frontend/src/integrations/booktime/bookFlow.ts:146–178`; `Frontend/src/integrations/booktime/slots.ts:32–39,104–120`; `Frontend/src/integrations/booktime/localTime.ts:1`.

`GameExternalBooking` stores the provider, but its unique key is only `(gameId, externalBookingId)` and the index is only `externalBookingId`. The linked-games lookup filters raw IDs without provider/club scope. A short integer or court-slot ID from another provider could collide. Use a stable scoped booking identity `(provider, external venue/club, external booking ID)` throughout lookup, unlink, cache and deduplication paths. Prefer an explicit schema identity over ad hoc prefixes; migrate existing links safely. Sources: `Backend/prisma/schema.prisma:902–918`; `Backend/src/services/booktime/booktimeGameLink.service.ts:37–57`; `Backend/src/services/game/gameExternalBooking.service.ts:186–189,580–601`.

Booktime verification exhausts upcoming and previous pages, recognizes cancelled rows, and throws on incomplete/nonadvancing pagination. Network errors are not interpreted as a missing booking. Keep this distinction for any later Weltner verification path. Source: `Frontend/src/integrations/booking/verifyBooktimeBooking.ts:7–32`.

Booktime cancellation first resolves linked games, then cancels upstream, unlinks locally and refreshes availability. Local unlink failures are logged after a successful cancellation. Creating a game after making reservations uses rollback attempts if booking or game creation fails. These are multiple remote operations, not an atomic transaction. Sources: `Frontend/src/integrations/booktime/bookFlow.ts:194–212`; `Frontend/src/components/createGame/BooktimeCreateGameConfirmModal.tsx:239–247,286–311,337–363`.

New writes need an operation record and an explicit unknown-outcome state. A timeout after sending a create/cancel request does not prove failure; avoid automatic duplicate POSTs. Reconcile through a supported lookup/idempotency key or require club resolution. Separate “upstream reservation succeeded; local link failed” from “upstream rejected reservation”. A post-create snapshot refresh must not erase evidence that the reservation succeeded. These are recommendations arising from the multi-step flow above.

## Nspadel: useful precedent and pitfalls

Nspadel's backend validates the court/duration, takes name/phone from the Bandeja profile, checks occupancy and inserts a reservation. Because its upstream row cannot be read back, it generates `nspadel:{court}:{date}:{start}` as the external ID and reports confirmed. The FE returns no upcoming list, has no verification implementation and throws a “cancel via club” error on cancellation. Sources: `Backend/src/services/nspadel/nspadelBookings.service.ts:290–360`; `Frontend/src/integrations/booking/providers/NspadelClubBookingProvider.ts:23–76`; `Frontend/src/integrations/nspadel/client.ts:236–239`.

Its create modal books courts sequentially and creates the game afterward. The catch block reports an error but does not undo already completed reservations or persist recovery state. This is especially risky for multi-court booking or a game-save failure. Its synthetic slot ID is a local association key, not a provider-issued confirmation or an upstream cancellation handle. Do not infer those capabilities for Weltner. Source: `Frontend/src/components/createGame/NspadelCreateGameConfirmModal.tsx:84–150`.

## Proposed implementation slices

1. **Availability-only integration.** Add validated Weltner configuration and court mappings, fetch/normalize observed slots, and render exact date/start/duration options with freshness and error states. Keep an external booking link as an initial fallback. Add backend occupancy support deliberately if that is a requirement.
2. **Capability-aware booking contract.** Represent authentication mode, create/list/verify/cancel capabilities and cancellation destination. Extend the result beyond `externalBookingId/start/end/price` to distinguish confirmed, submitted/pending and unknown outcomes. Payment or club approval, if discovered, must be modeled explicitly; these are not existing Weltner facts. Unsupported methods should be absent or return typed unsupported outcomes.
3. **One-court booking.** After the actual POST response and club confirmation behavior are established, add authenticated Bandeja submission with contact review, live slot recheck, durable operation tracking, scoped identity and recovery. Only a confirmed reservation contributes to `EXTERNAL_FULL`/`EXTERNAL_PARTIAL` coverage. Keep local game creation recoverable independently of an irreversible upstream submission.
4. **Management parity only with evidence.** Add existing-reservation import, verification and cancellation only if real customer/provider APIs support them. Otherwise explicitly label locally recorded bookings and direct cancellation to the club. Multi-court booking should wait for a demonstrated compensation/recovery approach.
5. **Focused verification.** Fixture-test response parsing, exact slot choices, wrong-club court IDs, timezone boundaries, concurrent slot loss, duplicate submit, response-lost-after-write, game-save failure, unavailable cancellation, unknown outcome and scoped-ID collisions. Re-run existing provider contract, Booktime normalization/refresh, coverage and rollback tests for regressions. Execute heavy commands only through serialized repository scripts.

Do not invent endpoints to fill those gaps.
