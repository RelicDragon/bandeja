# PRD 351: PRD: Referral program on top of link-to-app attribution

## Problem Statement

Growth is word of mouth, but the app cannot tell who brought whom. Link-to-app attribution records UTM and an `aid` and attaches it at registration, yet there is no notion of a referring user, no reward, and no place for a player to share a personal link.

## Solution

Give every user a referral link and code that rides the existing attribution pipeline. When a referred user registers and finishes their first game, both sides receive coins via `NEW_COIN`. Profile shows referrals and pending rewards. Admin sees referral stats next to link-to-app campaigns.

## User Stories

1. As a player, I want an "Invite friends" card with my link and code, so that I can share it anywhere.
2. As a player, I want the share to use the native share sheet on mobile and copy on web.
3. As a new user arriving by referral link, I want the code applied automatically at registration, so that I do not type it.
4. As a new user, I want to enter a code manually within 7 days if the link did not carry it.
5. As a referrer, I want coins when my friend finishes their first game, not just registers, so that rewards reflect real players.
6. As a referred user, I want a welcome coin bonus at the same moment.
7. As a player, I want to see who I referred and their status (registered / played), so that I can nudge them.
8. As an admin, I want referral counts and conversions in the link-to-app dashboard, so that campaigns and referrals are comparable.
9. As an admin, I want self-referral and duplicate-device abuse blocked.
10. As a developer agent, I want referral to be a field on the existing attribution row, not a parallel system.
11. As a referrer, I want to invite a friend straight into a specific game, so that the invite is concrete ("come play Tuesday").
12. As a referrer, I want a notification when my friend joins and when they play their first game, so that the loop feels alive.

## UX / UI Design

### Invite friends card
- **Profile → General**, above Wallet: a card with a two-avatar illustration (the user's avatar plus a dashed placeholder), headline "Bring a friend, both get 50 coins", subline "They get 25 when they play their first game." Primary **Share invite** (native share sheet with the link and a short message), secondary **Copy code** showing the code in a monospace pill (`BNDJ-7K2Q`) that copies on tap with a "Copied" toast.
- Below the card, a **Your invites** list: rows with avatar/initials, name or "Pending", and a state chip **Invited** (grey), **Joined** (sky), **Played · +50** (green). Empty state: "No invites yet. Your first friend is one tap away."

### Share surfaces
- The existing `ShareModal` for games gets a **Invite a friend to this game** option that shares a game link carrying `?ref=CODE`, so a new user lands on the game after registering.
- Home invite-friend empties (existing) route to the same share action.
- Telegram: `/invite` replies with the personal link.

### Landing and registration
- The static `/link-to-app/` landing shows a small "Invited by Marko" chip when `ref` resolves (public name only), plus the store buttons unchanged.
- Register screen: when a referral is captured, a quiet banner "You'll get 25 coins after your first game" with the referrer's avatar. When not captured, a collapsed **Have a code?** text link expands a code field (uppercase, auto-format with the dash, inline validation with a 300 ms debounce and a green check).
- Onboarding (from the onboarding PRD) shows the same banner on the Welcome step.

### Reward moment
- Referrer push "Ana played her first game. +50 coins!" and referred push "Welcome bonus: +25 coins". Opening either lands on the Wallet with the new transaction row highlighted for 1 s (soft sky tint) and a short coin count-up on the balance.
- The Wallet balance uses the existing `TRANSACTION` notification pipeline; no confetti, one count-up.

### Admin
- Link-to-app page gets a **Referrals** table: referrer, invited, joined, played, rewarded, with date filters and CSV export, next to the existing campaign labels.

### Edge cases
- Code invalid or self: field error "That code isn't valid" / "You can't use your own code".
- Window expired: the code field is hidden after 7 days with a caption "Referral codes can be added within 7 days of joining".
- Cap reached: the invite card shows "You've reached 50 rewarded invites. Keep inviting, no more coins" without hiding the share button.

### Accessibility
- Code pill is a button labeled "Copy invite code B N D J 7 K 2 Q"; state chips have text; share action is a native control.

## Implementation Decisions

- `User.referralCode` unique short code (generated lazily, 8 chars from an unambiguous alphabet). `LinkToAppAttribution.referrerUserId` nullable; `User.referredByUserId` nullable set at conversion via the existing `POST /auth/attribution` merge (first-touch rule: referrer never overwritten). `ReferralReward` (referredUserId unique, referrerUserId, rewardedAt, referrerTxId, referredTxId).
- Link: `https://bandeja.me/link-to-app/?ref=CODE` (also `/games/:id?ref=`) → static landing stores `ref` next to `aid` (cookie, localStorage, clipboard `bandeja-aid:`); `useDeepLink`/`authPersistence` carry it to registration. Manual entry `POST /users/me/referral-code` valid ≤7 days after registration and only if `referredByUserId` is null.
- Reward: on the referred user's first `GameOutcome` (FINAL GAME/TOURNAMENT/LEAGUE, rated or not), grant `NEW_COIN` to both via the existing admin-grant transaction service with reason `REFERRAL`. Amounts from Platform Settings (defaults 50/25). Idempotent by `ReferralReward`.
- Abuse: reject same user id, same verified Telegram id or phone, same push token or device id at conversion; cap 50 rewarded referrals per referrer; admin can revoke.
- Notifications: reuse `TRANSACTION` with a referral message variant; add `REFERRAL_JOINED` (referrer only) → `sendWalletNotifications`.
- Landing referrer name: `GET /api/public/referral/:code` returns first name and avatar only.
- Admin: `GET /admin/referrals` with filters; CSV via existing export helper.
- Telegram `/invite` command.

## Testing Decisions

- Attribution merge test: `ref` captured on both landing and game links, first-touch preserved, manual code window and validation.
- Reward service: fires once, both parties, abuse rules, cap, revoke.
- Static landing test for `ref` propagation (existing link-to-app tests pattern) and referrer chip.
- FE: invite card states, code field validation, register banner, wallet highlight.
- UI test plan: Profile invite card, Register with code, Share game with invite.

## Out of Scope

- Cash rewards or store credit outside coins.
- Multi-level referrals.
- Club-level referral programs.

## Design language (shared with every PRD in this set)

- **Mobile first.** Capacitor iOS/Android and mobile browsers are the primary target. Every overlay with an input lays out against the visual viewport via the keyboard contract (`Frontend/src/utils/keyboardLayout.ts`, `body.keyboard-visible`, `--overlay-bottom-inset`). Desktop gets the same components in the split layouts already used by Home/Find.
- **Surfaces.** Bottom sheets (vaul) for actions and detail, Radix dialogs only for destructive confirms, full-screen routes for destinations. Sheets open/close with the existing `[data-state='open'|'closed']` keyframes; all motion gated on `prefers-reduced-motion`.
- **Motion.** Framer Motion 12. Springs for entrance (stiffness 260, damping 24), 180–240 ms fades for state changes, layout animations for list reorders. Never animate more than one hero element at once. Number changes use a count-up tween ≤600 ms.
- **Color.** Tailwind `primary` (sky) for actions, semantic greens/ambers/reds for states, neutral surfaces from `tokens.css`. Premium members keep gold accents where the shell already applies them; new surfaces must read correctly in Light, Dark, Classic, and Premium.
- **Type and density.** One headline per screen, one primary action per sheet, secondary actions as text buttons. Cards keep the `GameCard` rhythm: date tile left, title row, info rows, right rail.
- **Icons.** lucide-react only. No emoji as icons; emoji allowed in copy where playful.
- **Feedback.** `react-hot-toast` for transient confirmations, inline banners for persistent state, skeletons (`GameCardSkeleton` pattern) for loading, `EmptyStateCard` for empties with one clear next action.
- **Accessibility.** 44 px tap targets, 4.5:1 text contrast, roles/labels on every control, arrow-key support on segmented controls, RTL verified for `ar`, all copy in the 11 app locales.
- **Copy.** Plain, second person, verbs first ("Confirm seat", not "Seat confirmation"). No jargon from the schema in user-facing text.
