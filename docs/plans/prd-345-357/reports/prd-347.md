## 2. Decisions that need a second opinion

**Auto-fill does *not* skip the level check.** `ParticipantService.acceptNonPlayingParticipant`
passes `skipLevelCheck: true`, because an organizer accepting by hand is a conscious override. Auto-
fill has no human in the loop, so it pre-checks `validatePlayerCanJoinGame(..., { targetIsOtherUser: true })`
with the level check **on** before delegating. The PRD says "gender and level rules still apply"
(User Story 8), and the settings helper promises it in copy. The delegate call still runs its own
`skipLevelCheck: true` validation, which is a strict subset, so behaviour for the manual path is
byte-identical. Covered by `gameSeat.integration.test.ts` §3 (low-level player stays queued, next
one is seated).

**`seatOpened` re-derives instead of trusting `freedCount`.** It reads the roster and returns early
when there is no genuinely open seat. That is what makes the substitution trigger safe (the seat is
handed straight to the substitute, so nothing fires) and what makes a double trigger harmless.

**Invite decline is gated.** An `INVITED` row never counted toward slots, so firing on every decline
would raise the pill on half-empty games. `seatOpenedFromInviteDecline` only fires when
`playing + invited` was exactly `maxParticipants` before the decline — i.e. the decline is what made
a seat available. See §5 for the honest caveat.

**`togglePlayingStatus` added as a sixth trigger.** It frees the same seat `leaveGame` does and
already sits next to `schedulePendingInviteSlotOpenNotify`. Not in the PRD's list; dedupe makes it
harmless and omitting it would have been a visible hole.

**The seated-from-queue header is its own component, not an edit to `AttendanceCard`.** PRD 346 owns
that file. `SeatedFromQueueBanner` renders immediately above it and degrades to nothing when the
attendance card is absent, so neither PRD has to know about the other's markup.

**`sortDayGroupGames` is a stable partition, not a re-sort.** `UpcomingGamesList` sorts its
*finished* list **descending** before grouping, and its private `groupGamesByDate` never re-sorted
within a day. A naive "pilled first, then by start time" would have silently flipped that list.
The helper therefore only compares the boost; `utils/groupGamesByDate.ts` keeps its own explicit
ascending sort before calling it. There is a regression test for exactly this.

## 3. Contract deltas

1. **There is no `gameSeat.routes.ts`.** CONTRACT §8/§2.2 says enrichers must be registered at
   import time of a module the app loads, and names the feature's route file as the reliable path —
   but the Wave 2 backend scaffold created 13 routers and none for PRD 347, because PRD 347 adds no
   endpoints. `gameSeat.service.ts` does `import './spotOpenedEnricher'` at module scope, and
   `participant.service.ts` imports `gameSeat.service` statically, so the chain reaches `app.ts`
   through `routes/index.ts` → `game.routes.ts` → `game.controller.ts`. **If anyone later makes the
   participant-service import dynamic, the enricher stops registering and the pill silently
   disappears from Find.**
2. **`SpotOpenedInfo` is used for the socket payload only.** CONTRACT §5.6 fixes the card field as
   `spotOpenedAt?: string | null`, which is what the enricher returns; the richer `SpotOpenedInfo`
   shape types `game-seat-opened`. Neither type was changed.
3. **One new `NotificationData` field**, `seatedFromQueue?: string`. The "You're in!" push and the
   ordinary spot-opened push are both `GAME_SPOT_OPENED`, and the client needs to tell them apart to
   decide between `?join=1` and the one-time header. Mirrored in
   `Frontend/src/services/pushNotificationService.ts`'s local `NotificationData`.
4. **No new Telegram callback prefix.** CONTRACT §5.3 allocates `at`/`sr`/`wx`/`pi`; PRD 347 needed
   none. "Join now" is a URL button (`/games/:id?join=1`) and *Show Game* reuses the existing `sg:`
   handler. `bot.service.ts`'s regex is untouched.
5. **`autoFillFromQueue` had to be added to `GAME_UNCHECKED_SCALAR_KEYS`** in `update.service.ts`.
   The contract lists the column but not the allowlist; without the entry the toggle is silently
   dropped by `pickUncheckedGameScalars`.
6. **Two new `@theme` animations in `styles/tokens.css`.** There is no existing pulse or one-shot
   sweep utility (`--animate-shimmer` is `infinite`), and a two-iteration CSS animation cannot be
   expressed with Tailwind's built-ins.

## 5. Known gaps

1. **`INVITE_DECLINED` is reachable but narrow.** `InviteService.declineInvite` returns early unless
   `participant.status === 'INVITED'`, and `INVITED` never counts toward slots — so "decline of a
   *PLAYING* invite", as the PRD words it, does not exist in the current code. I implemented the
   nearest true thing (the decline that un-fills a full roster). If the intent was "any invite
   decline raises the pill", change the guard in `GameSeatService.seatOpenedFromInviteDecline`;
   nothing else moves.
2. **`SUBSTITUTION` never fires today.** `substitute()` requires `resultsStatus === IN_PROGRESS`
   (locked) and hands the seat straight over, so both guards stop it. The call is wired so a future
   rollback path goes through the same funnel. Documented in `docs/plans/.../domains/prd-347.md`.
3. **The roster "Open spot" slot lives in my queue panel, not inside `GameParticipants.tsx`.** That
   file is a large shared surface (PRD 346's attendance dots are in it) and editing its three
   carousel branches was too collision-prone. The auto-filled avatar's slide-in comes from the
   `motion.div layout initial={{opacity:0,x:-8}}` that file already has on participant rows — which
   means **that particular animation has no reduced-motion gate**. That is pre-existing, not
   something I introduced; worth a follow-up.
4. **The `?join=1` consumer is mounted inside `renderTabContent()`**, so it runs on the details tab.
   Every entry point I control (push tap, Telegram button, deep link) lands there with no `tab`
   param. A link that also carried `?tab=chat&join=1` would not fire the join.
5. **No test for `notifySpotOpened`'s claim/release loop against a real DB.** The integration test
   asserts the resulting `SpotOpenedDelivery` rows; the retry policy itself is covered by the pure
   `sendWithBackoff` test with an injected sleep. A DB test of "transient failure releases the
   claim" would need a stubbed `notificationService`.
6. **The `gameSeat.service` → … → `invite.service` / `update.service` import cycles.** I checked:
   both already cycle to themselves through `game.service` / `chat.controller` without my edges, so
   I added no new class of problem. `playIntentMatch.service` is reached through a **deferred**
   `await import(...)` in `spotOpenedIntentRecipients.ts` — deliberately, because
   `participant.service.ts` already avoids that module statically for the same reason. Please keep
   it deferred.
7. **Zero type checking.** I could not run `tsc`. The likeliest failure points, in order:
   `toGameInfo`'s mapping onto `GameInfo` (Prisma `null` vs optional), `canMutateGameRoster(game)`
   accepting Prisma enum types structurally, and `IntentScorableGame` vs the `SeatGame` select.
