## 2. Contract deltas

1. **The backend `StorySegment` union arm is real, not decorative.** The contract's checklist implies
   a `MONTHLY_RECAP` feed arm; a feed arm would have been dead code, because the PRD forbids an
   unshared recap from being visible to anyone. So the arm is produced by
   `recapSegments.ts` and returned by `GET /users/me/recaps/:monthKey` — one typed contract shared
   by both sides, zero duplication of the slide-building logic on the client.
2. **A sixth endpoint, `POST …/viewed`.** The PRD lists four. "Disappears from the rail after
   viewing but stays in Profile" needs a write, and doing it implicitly inside `GET /:monthKey`
   would mean a prefetch could silently consume the bubble.
3. **Backend copy is not in `utils/translations.ts`.** That file is 4 000 lines and shared by every
   agent in this programme; the ~12 recap strings live in `recapCopy.ts` / `recapPushCopy.ts`
   instead. Same `t(key, lang)` semantics, all 11 languages, no merge surface.
4. **"One game in September" reads "1 game in September".** `localeParity.test.ts` requires every
   plural form to carry the same placeholders as the English `_other`, so the `_one` form cannot
   drop `{{count}}`. Contract rule beats PRD wording (CONTRACT §0); the meaning is unchanged.
5. **The results artifact renderer is an AI image pipeline, not a card renderer.** PRD 353 says the
   shared slides and the `recap-card` go "through the results artifact renderer
   (`gameResultsArtifact/`)", but that directory is Replicate/LLM generation for game photos and
   summaries — it cannot render a stats card. I used the actual house precedent for a
   server-rendered card, `telegram/bracket-summary-image.service.ts` (SVG → `sharp` → `S3Service`),
   and kept the *visual* language of the results share card. S3 and the 24 h story TTL are exactly
   as the PRD asks.
6. **Best partner is month-scoped and computed in the recap builder.** `userPerformanceInsights`
   loads a user's *entire* history per sport — unusable in a sweep over thousands of users, and it
   is not month-scoped. The recap reuses that module's `resolveStreakResult` for W/L/T
   classification but tallies partners itself over the month's decided matches.
7. **`EntityType.EVENT` and `EntityType.BAR` are excluded** from the recap's games. They are not
   personal results. Not stated in the PRD; stated here so a critic does not read it as a bug.
8. **Rail visibility.** `StoriesRail` used to return `null` when the viewer has no follows. A recap
   must not depend on the social graph, so the guard is now
   `railHidden && !recapRail.bubble`, and the create bubble / empty hint are suppressed
   individually instead.

## 4. Known gaps

1. **No fonts are guaranteed on the render host.** `recapSlideImage.renderer.ts` asks for a Noto
   stack (`Noto Sans Arabic`, `Noto Sans SC`, `Noto Sans JP`, `Noto Sans Thai`,
   `Noto Sans Devanagari`). If the production container has no CJK/Arabic/Thai/Devanagari font,
   librsvg will render tofu for those languages in the **shared images and the exported card**
   (the in-app reel is unaffected — it is HTML). This needs a devops check, and possibly a
   `fonts-noto` package in the image. Flagged under Manual verification.
2. **Sparkline density.** A month with 30 level events draws 31 points into a 220×60 box. It reads
   fine, but I did not downsample; a very active month's sparkline is busy.
3. **Share is not resumable.** `shareRecapToFollowers` renders and uploads every slide before it
   opens its transaction; if the process dies mid-upload, the orphaned S3 objects are never
   collected (no story row references them). Low volume, but it is a real leak.
4. **Only the level slide can be `sensitive`.** That is what the PRD asks for, and the share sheet's
   default is written against it. If a second producer of `sensitive` is ever added, the
   "off by default" hint copy will need to stop naming the level case implicitly.
5. **No admin backfill surface.** `runOnce({ force: true, monthKey })` exists and is the intended
   entry point for a manual regeneration, but there is no admin page or CLI for it.
6. **Low-activity eligibility is a two-query sweep.** `findLowActivityUserIdsForMonth` pages the
   90-day-active users and then subtracts the ones who played last month. On a very large instance
   the second query's `in` list is bounded by the page size (200), which is fine, but the first
   query scans a 90-day window of `GameOutcome` each page.
7. I could not run the type checker, the linter or any test. Everything below is written but
   unverified by a compiler.

## 7. Invariants worth adding to `docs/product/constraints.md`

Two, both load-bearing:

1. **An unshared `MonthlyRecap` never creates a story row.** Generation writes exactly one
   `MonthlyRecap`; only `shareRecapToFollowers` in
   `Backend/src/services/recap/recapShare.service.ts` may create a `UserStory`. Followers receive
   *rendered images*, never the payload, so a slide the owner unticked can never leak.
2. **Recap idempotency is the unique `(userId, monthKey)`, not a `Set` and not an upsert.**
   `generateMonthlyRecap` in `Backend/src/services/recap/recap.service.ts` does a plain `create` and
   treats `P2002` as "already done" (`created: false`); `monthlyRecapPass.ts` only pushes when
   `created` is true. Turning that `create` into an `upsert` would make every catch-up run report
   success and would re-push on the 2nd and 3rd of the month.
