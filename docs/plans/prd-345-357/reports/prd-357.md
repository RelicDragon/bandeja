Thresholds (all named constants in `weatherRisk.ts`):
`POP ≥ 60 %`, `≥ 1 mm/h`, `wind ≥ 40 km/h` → `likely`; `≥ 85 %` or `≥ 4 mm/h` → `heavy`;
thunderstorm, `wind ≥ 60 km/h` or `≥ 8 mm/h` → `storm`. Card horizon 48 h.
Windows: first `11.5–12.5 h`, second `1.5–2.5 h` (disjoint, so one pass can never alert twice).

## 2. Contract deltas

1. **`weatherForecast.service.ts` needed a new export.** The contract says to reuse the forecast
   service and its cache, but its public API only offers a per-city blocking window
   (`getWindowForCity`) or a per-game summary point. The scheduler and the Find enricher both need
   the **hourly window for many games at once, without touching the provider**. I added
   `getCachedForecastPayloadsForCities(cityIds, now)` — cache-only, one query, reusing the file's
   own freshness helpers. No second provider path and no cache bypass.
2. **`PUSH_INVITE_ACTION_ALLOWED_ACTIONS` behaves exactly as the Wave-2 report describes.** My test
   pins `weather → ['keep']` and that `weather`/`accept` is refused on sign.
3. **`NotificationData` needed four new optional fields** (`weatherKeepActionToken`,
   `moveIndoorActionTitle`, `weatherDeepLink`, `weatherSeverity`). The contract only mentions
   `keepActionTitle`, which was already there but insufficient — there was nowhere to put the
   signed token or the deep link.
4. **A new `SystemMessageType` was unavoidable.** The PRD requires the chat line
   "Moved to court 1 (indoor)". `GameUpdateService.updateGame` announces club and time changes only,
   and teaching it to announce every court change would put a chat line on unrelated edits. See §3.
5. **`docs/domains/weather.md` is one paragraph long** and says nothing about alerts; the delta is
   staged as instructed rather than applied.
6. **`GAME_WEATHER_ALERT` Telegram delivery goes through the dedicated telegram service**, not
   through `NotificationService.sendNotification` — that method only fans out to Telegram for the
   four play-intent types. I check `NotificationPreferenceService.doesUserAllow(..., TELEGRAM,
   SEND_WEATHER_ALERTS)` explicitly before sending, so the preference is honoured on both channels.

## 4. Known gaps

1. **Native push shade actions are not wired.** The backend emits `actions: [{ id: 'moveIndoor' },
   { id: 'keep' }]` plus the signed token and the deep link in `data`, exactly like PRD 346's
   attendance actions. The Android `InviteNotificationHelper` / iOS equivalents only know about the
   invite `accept`/`decline` pair, so the buttons will not appear on a device until somebody extends
   the native helpers. Tapping the push body works today (the deep link is handled). PRD 346 has the
   same gap; whoever closes one should close both.
2. **The card pill uses the locale's default hour convention, not the user's 12 h/24 h preference.**
   `GameCardHeaderTags` has no access to `resolveDisplaySettings(user)` and adding a prop would have
   meant editing the `GameCard` call site that another agent owns. The banner *does* use the user
   preference. Cheap to close later by threading one prop.
3. **`weatherRiskDisplay.ts` mirrors two backend thresholds** (60 % and 40 km/h) to answer "is this
   rain or wind?" for the card payload, because `WeatherRisk` is a fixed shape with no
   `windDriven` flag. The function prefers the flag when one is present (the banner's richer
   payload does carry it), and the duplication is called out in the file header.
4. **No integration test for `getIndoorAlternatives` against a real club.** The availability rule is
   covered by fixtures; the Prisma query around it (sport filter, active courts, club resolution)
   is only covered manually.
5. **`getWeatherAlertState` is queried once per game-details open even for indoor games.** There is
   no client-side signal to skip it. It is rate-limited and cheap (1–3 indexed queries), but a
   future optimisation could short-circuit on a `weatherRisk` already present on the loaded game.
6. **The move-indoor sheet moves one court at a time and always sets `courtIds: [court.id]`.** For a
   two-court game that means the second court is dropped when the organizer moves the first. The PRD
   says "handles one court at a time"; this is the simplest reading, but a multi-court club may want
   "replace only the outdoor one". Flagged rather than guessed.
7. **`weatherAlertState.lastEvaluatedAt` is written on every evaluated at-risk game each pass**
   (one `UPDATE` per game in the two 1-hour windows). Bounded and indexed, but it is a write the
   feature could avoid by only persisting on change.
