## 1. Done

### 1.1 Backend — the privacy gate

`Backend/src/services/game/availableGamesStructuralWhere.ts`

- `AvailableStructuralFilters.liveOnly?: boolean`.
- New exported constant **`LIVE_RAIL_WHERE`** = `{ resultsStatus: 'IN_PROGRESS', isPublic: true,
  showOnLiveRail: true }`, applied by `appendStructuralFiltersToWhere` as the **first** `AND`
  clause so the gate is never conditional on another filter matching.
- `parseStructuralFiltersFromQuery` was deliberately **not** widened: a Find query must not be able
  to flip itself into live mode. `liveOnly` is only ever set in code.

This one constant is what every live surface reads. Four consumers, one definition.

### 1.2 Backend — the live summary

`Backend/src/services/game/liveGameSummary.ts` — **new, pure** (no prisma, no env). Derives
`LiveGameSummary` from the envelope already stored in `Match.metadata.liveScoring`:

- `readLiveSummarySets`, `readActiveSetIndex`, `readCurrentGameScores`, `leadingTeamNumber`,
  `buildLiveGameSummary`, `liveEnvelopeUpdatedAtMs`, `formatSetScoreLine`.
- Point rendering covers `regular` / `deuce` / `advantage` / within-set tie-break, and returns
  empty strings for `points`-mode sports (americano and friends have no sub-game score).
- `setScores` covers every set **up to and including** the running one, so the card shows
  `6–4 3–2` rather than only completed sets.
- `revision` is copied straight off the envelope and propagated into the card.
- Returns `null` for a match with no usable state, so a cleared or legacy blob never produces a
  half-empty card.

`Backend/src/services/game/liveRailOrder.ts` — **new, pure**: `LIVE_RAIL_FIND_LIMIT = 10`,
`LIVE_RAIL_HOME_LIMIT = 3`, `LIVE_RAIL_MAX_LIMIT = 20`, `sortLiveRailGames`,
`clampLiveRailLimit`. Split out of the service purely so the ordering rule and the caps are
unit-testable without a database.

### 1.3 Backend — the rail query

`Backend/src/services/game/liveGames.service.ts` — **new**.

```ts
export async function listLiveGames(params: { cityId; viewerUserId?; limit? }): Promise<LiveRailGame[]>
export async function findLiveRailGame(gameId: string): Promise<LiveRailGame | null>
export async function liveSummariesForGameIds(ids: string[]): Promise<Record<string, LiveGameSummary>>
export async function liveRailGameIdsForUsers(userIds: string[]): Promise<string[]>
export type LiveRailGame = { …slim game facts…, viewerIsPlaying, followedSeason, liveSummary }
```

- Uses a dedicated slim `select` (club/court/city, PLAYING participant ids, rounds → matches →
  teams → players), not the Find card projection — the rail needs the match teams, which the Find
  card does not carry.
- A game with several boards resolves to the match whose envelope was touched most recently, with
  the highest `matchNumber` as the tie-break.
- Order: the viewer's own game, then followed-season fixtures, then start time ascending.
- Over-fetches `2 × MAX_LIMIT` rows and drops games with no usable live state before slicing.
- `listLiveGames` is what PRD 356's `/live` calls **in process** — the bot never HTTP
  round-trips to its own API, and this is also what guarantees the two surfaces agree.

### 1.4 Backend — enrichment

`Backend/src/services/game/liveGamesEnricher.ts` — **new** side-effect module registering
`registerAvailableGamesEnricher('liveSummary', …)`, imported by `liveGames.routes.ts` (which is
mounted from `routes/index.ts`, so registration always runs). Returns `liveSummary: null`
explicitly for non-live cards so a stale summary is cleared rather than left behind.

### 1.5 Backend — endpoints

`Backend/src/controllers/liveGames.controller.ts` + `Backend/src/routes/liveGames.routes.ts`
(the pre-created router, mounted at `/api/live`):

| Route | Auth | Notes |
|---|---|---|
| `GET /live/games?cityId&limit` | `authenticate` | defaults to the viewer's city; `[]`, never 404, when nothing is live |
| `GET /live/games/:id` | `authenticate` | one watchable game, for the details Live block |
| `POST /live/games/:id/spectator-token` | `optionalAuth` + rate limit | mints the **existing** `signLiveSpectatorToken` |

The spectator mint:

- **does not widen** `POST /results/game/:gameId/matches/:matchId/live-spectator-token`; that one
  stays `requireCanModifyResults` for arbitrary matches;
- only ever signs for a game that passes `LIVE_RAIL_WHERE`, and answers the **same `404`** for
  private, non-live and opted-out games, so it cannot be used to probe game visibility;
- runs under `optionalAuth` because the broadcast page is already public with a
  `?spectatorToken=`, so a shared live link has to work for a signed-out viewer — the gate is what
  protects the data, not the session;
- is rate limited to 60 per 15 min per client key (`rateLimitKeyFromRequest`).

### 1.6 Backend — the follower push

`Backend/src/services/live/liveGameNotify.service.ts` — **new**.

- `notifyFollowersGameWentLive(gameId)` and the fire-and-forget
  `notifyFollowersGameWentLiveInBackground(gameId)`.
- Re-checks all three gate conditions and returns a typed `skipped` reason otherwise.
- Audience mirrors `playIntentFollowerAudience.ts`: followers of a PLAYING participant, same city,
  sport enabled, neither side blocked, minus the players themselves. One notification per
  recipient, naming the first followed player on court.
- Dedupe is `LiveGameNotifyDelivery`, **claimed before dispatch** (`create`, catching `P2002`), so
  two concurrent transitions cannot both send and a restart cannot resurrect the chance.
- Hooked into `Backend/src/services/results/matchLiveScoring.service.ts` at the point where the
  game transitions to `IN_PROGRESS`, never awaited.

`Backend/src/services/live/liveCopy.ts` — **new** copy module (`liveT(key, lang, params)`), the
same pattern PRD 345 established with `gameSeriesCopy.ts`. Covers the push copy, all of `/live` and
`/play`, and the bot menu descriptions, in all 11 bot languages.

### 1.7 Backend — game settings

`Backend/src/services/game/update.service.ts` — `'showOnLiveRail'` added to
`GAME_UNCHECKED_SCALAR_KEYS` so the existing `PUT /games/:id` path can persist the toggle.

Behaviour worth calling out:

- **Only visible cards are subscribed.** `useLiveGames` retains exactly the rooms it renders and
  releases every one of them on unmount.
- **Revision guard.** `applyLiveScoringFrame` returns the *same object reference* when a frame is
  stale, for another match, or unreadable — so a memoised card does not even re-render, and a late
  frame can never roll the score backwards. The overlay also wins over a background refetch only
  when its revision is higher.
- **Freeze, never blank.** Socket loss swaps the footer for a grey "Reconnecting"; the scores stay.
  On reconnect the rail refetches, because missed frames are not replayed.
- **One hero at a time.** The only looping animation is the 2 s dot; the digit slide and the
  leading-side glow are one-shot. Every one of them has a reduced-motion path, including the
  `layoutId` shared-element transition, which is dropped entirely (`layoutId={undefined}`).
- **RTL.** Logical properties throughout (`text-start`/`text-end`, `border-s`, `end-0`,
  `rtl:rotate-180`, `rtl:space-x-reverse`). No `ml-`/`mr-`/`pl-`/`pr-`/`left-`/`right-`.
- **44 px** on every control: cards, the Watch buttons, the See all link, the spectator bar
  buttons and the overflow rows.

## 2. Contract deltas

1. **"Followed-season fixtures first" has no backing model.** There is no season-follow table.
   Implemented as *the viewer is a non-withdrawn `LeagueParticipant` in that season*, matched
   through `Game.parent.leagueSeason.id`. If a real follow model lands later, only
   `followedSeasonIds()` changes.
2. **The rail does not reuse the Find card projection.** CONTRACT §5.6 puts `liveSummary` on the
   Find card (done, via the enricher), but the rail itself needs the *match teams*, which no Find
   card carries. `listLiveGames` therefore has its own slim select. The two paths share
   `LIVE_RAIL_WHERE` and `buildLiveGameSummary`, which is where agreement actually matters.
3. **`GET /live/games/:id` is not in the contract.** The game-detail payload carries no
   `liveSummary`, so the details Live block needs a way to fetch one. The alternative — widening
   the game-detail read service — is a much larger blast radius in a file other agents own.
4. **The spectator mint is `optionalAuth`, not `authenticate`.** Reasoning in §1.5. If the
   orchestrator prefers `authenticate`, it is a one-word change in
   `Backend/src/routes/liveGames.routes.ts`; the cost is that a shared broadcast link stops
   working for signed-out viewers, which reads as a regression against user story 3.
5. **No push action button on `FOLLOWED_USER_LIVE`.** The PRD says "with **Watch** action". Push
   actions in this codebase are identifiers dispatched by `pushInviteAction.controller.ts`, not
   URLs, and there is no handler to register for pure navigation. The notification's own tap target
   (`data.gameId`) is the Watch affordance. A dead button would have been worse.
6. **Backend copy went into a namespaced module** (`services/live/liveCopy.ts`) rather than
   `utils/translations.ts`, following the precedent `gameSeriesCopy.ts` set in this same programme
   and for the same reason (eleven insertions into a 3900-line shared file).
7. **`liveOnly` is code-only.** It is not parsed from the query string, so no Find request can turn
   itself into a live query.

## 3. Files I could not touch

None blocked me. Two things for the orchestrator:

1. **`package.json` test wiring** — see §5.
2. **`docs/product/constraints.md`** — one invariant is worth adding verbatim:

   > **PRD 349 — the Live-now gate.** `LIVE_RAIL_WHERE` in
   > `Backend/src/services/game/availableGamesStructuralWhere.ts` (`resultsStatus = IN_PROGRESS`
   > **and** `isPublic` **and** `showOnLiveRail`) is the single definition of "a stranger may watch
   > this game". Do not inline those three conditions anywhere. Every consumer —
   > `listLiveGames`, `findLiveRailGame`, `liveSummariesForGameIds`, the spectator-token mint,
   > Telegram `/live`, and `notifyFollowersGameWentLive` — must go through it. Dropping any one of
   > the three exposes a private or opted-out game on a public surface.
   >
   > **`LiveGameSummary.revision` must be propagated.** It comes from
   > `Match.metadata.liveScoring.revision` and is what lets the rail drop an out-of-order socket
   > frame (`Frontend/src/features/live/liveSummaryUpdate.ts`). Removing it silently reintroduces
   > scores that jump backwards.

## 4. Known gaps

1. **No `tsc` / lint / test run.** I could not run any of them. The riskiest spots are the
   `Prisma.GameGetPayload<{ select: typeof liveGameSelect }>` inference in `liveGames.service.ts`
   and the `as const satisfies Prisma.GameWhereInput` on `LIVE_RAIL_WHERE`.
2. **The shared-element transition is best-effort.** `layoutId` is set on both the rail card's
   score block and the details Live block, but the *broadcast header* itself is
   `LiveScoreShell`, which I did not modify — so tapping a card animates into the details block,
   not into the broadcast scoreboard. Wiring `layoutId` into `LiveScoreShell` means editing the
   live-board component tree, which felt out of proportion to the payoff and risky for the
   scoring surface. Flagged as the one UX item short of the PRD text.
3. **Only the live-scoring transition fires the follower push.** `results.service.ts` also moves a
   game to `IN_PROGRESS` (undoing a FINAL result, bar results). Those paths do not notify. That is
   arguably correct — "went live" means someone started scoring — but if the orchestrator wants
   full coverage, `notifyFollowersGameWentLiveInBackground(gameId)` is idempotent and safe to call
   from any of them.
4. **`isReconnecting` is socket-state-derived, not per-card.** If one card's room fails to join
   while the socket is up, that card shows fresh-looking data. Per-room health is not exposed by
   `gameRoomMembership`.
5. **No Playwright coverage.** The UI test plan is written; the automated cases are Vitest and
   ts-node only.
