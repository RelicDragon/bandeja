## 2. Deviations from the contract / PRD (and why)

1. **Cursor shape.** CONTRACT §5.5's pattern is `id < cursor` descending by id. That cannot express
   a leaderboard ordering (win rate, then games, then recency, then ids, with `NULLS LAST` on two
   columns — mixed-direction keyset). The cursor is therefore an **opaque base64url
   `[offset, fingerprint]`**, where the fingerprint is `cityId:sport:period:sort`; a cursor from a
   different filter set is rejected with `400 errors.pairs.invalidCursor`. Ordering, paging and
   ranking happen in Postgres (`ORDER BY … LIMIT … OFFSET …`), so only one page is ever materialized
   in Node — the scaling hazard the contract calls out is addressed. Ranks stay continuous, which an
   id-keyset cursor could not guarantee.
2. **`assignPairRanks` removed** from `pairRankingOrder.ts`. The comparator is a *total* order (every
   chain ends on the pair ids), so no two pairs genuinely tie, and competition ranking would have
   disagreed with the SQL `ROW_NUMBER()` the materialized path uses and with the cursor offsets.
   Ranks are positional (`offset + indexOnPage + 1`) on both paths. A comment in the file records
   this.
3. **`period=10|30` is not served from `PairStat`.** The table stores all-time totals per
   `(sport, city, pair)`; a period dimension would multiply it by three and still be wrong the
   moment a window slides. Windowed requests re-derive from the games, batch by batch, bounded by
   city × sport × window, through the same pure rules. `period=all` — the default and the only value
   the UI starts on — is fully materialized, satisfying user story 9.
4. **Windowed chemistry uses the windowed solo counts**, not `UserSportProfile`. An all-time solo
   baseline against a 30-day pair rate compares two different things. `period=all` uses
   `UserSportProfile.gamesPlayed/gamesWon` exactly as the PRD specifies.
5. **Majority-of-matches denominator.** The PRD says "the majority of that game's matches"; taken
   literally that deletes every pair in any multi-court event (a duo in a 12-match, 8-player
   Americano scores 4/12). The denominator is "matches in which **both** players appeared". A
   genuinely rotating format still fails (1/3), which is the behaviour the rule exists to produce.
   Inherited decision, kept, documented in `partnerDetection.ts` and in the domain delta, and tested
   from both sides.
6. **"Recent together" cards are a purpose-built compact card**, not the full `GameCard`. Feeding the
   real `GameCard` would have meant pulling `FIND_CARD_GAME_SELECT` (and its contract asserter) into
   a pair endpoint for five rows. `PairRecentGameCard` reuses `GameCardDateTile` so the rhythm
   matches, adds the result chip the PRD asks for, and opens the game on tap.
7. **`pairs.names.display` and `pairs.row.summary` are composed in code**, not translated. Both
   templates are two placeholders plus punctuation (`&`, `·`), identical in all 11 locales, which the
   parity test would correctly flag as untranslated English. The *spoken* form used by screen readers
   (`pairs.names.spoken`, "{{first}} and {{second}}") is a real translated string.
8. **A period control was added to the Pairs tab** (All time / Last 30 days / Last 10 days). The
   player leaderboard exposes no period UI even though its API takes one; without this control the
   windowed path would be unreachable from the app. It is a second radio group next to the sort
   chips and shares the same keyboard behaviour.
9. **Pair sheet footer actions are gated on the viewer being one of the two.** "Create a team" and
   "Invite to a game" are meaningless for somebody else's pair; a third-party pair shows the stats
   and the history only.

## 4. `ChemistryChip` — final props (for PRD 353)

`Frontend/src/components/pairs/ChemistryChip.tsx`:

```tsx
export interface ChemistryChipProps {
  /** The two players of the pair, in any order; PRD 352 normalizes to `userAId < userBId`. */
  userAId: string;
  userBId: string;
  /**
   * The already-known chemistry in percentage points. Pass it wherever the caller
   * has it — the chip then renders without a request. Omit it and the chip fetches
   * the pair on its own.
   */
  chemistry?: number | null;
  /** Sport context for the self-fetching mode. Defaults to the viewer's primary sport. */
  sport?: Sport;
  className?: string;
}
export const ChemistryChip: React.MemoExoticComponent<(props: ChemistryChipProps) => JSX.Element | null>;
```

The two id props are unchanged from the scaffold, so **an existing `<ChemistryChip userAId=… userBId=… />`
keeps working**: it self-fetches via `queryKeys.pairs.detail` (`staleTime` 5 min) and renders `null`
until the data arrives, which is also the correct "not enough games together" state. For a recap
slide that already has the number, pass `chemistry` and it makes no request.

Behaviour: renders **nothing** when the value is `null`/`undefined`; green from `+5`, neutral below;
the number is always in the accessible name, so colour is never the only signal; long-press (and
hover, and focus) shows the "Win rate together vs. on your own" tooltip; 44 px tap target.

## 6. Known gaps

- **No integration test against `padelpulse_dev`.** The pipeline's symmetry and the aggregation are
  proven at the algorithm level (`pairStatPipeline.test.ts` drives the exact functions the service
  composes) and the ranking rules at the comparator level, but nothing exercises Prisma, the raw SQL
  or the HTTP layer. The raw SQL in particular (`::"Sport"` cast, `NULLS LAST`, the `ROW_NUMBER()`
  CTE) has only been checked by eye against the house pattern in
  `achievementLeaderboard.service.ts`. **This is the first thing to run.**
- **Nothing was executed.** No `tsc`, no lint, no test run, per the hard rules. Files were
  parse-checked with the TypeScript parser only; type errors are possible.
- The pair sheet's **"Invite to a game"** creates/reuses the team first and then opens the existing
  `AddUserTeamToGameSheet`. There is no team-less invite path in the codebase, and building one was
  out of scope ("Pair invites from the leaderboard beyond the existing team flow" is listed under Out
  of Scope).
- `GET /rankings/pairs` has **no dedicated rate limit**. It is authenticated, read-only and
  cursor-bounded; the windowed path is the expensive one and is bounded by city × sport × 30 days.
  If the orchestrator wants a limiter, `rateLimitKeyFromRequest` is the house pattern.
- The **admin rebuild has no UI**. It is an authenticated admin `POST`; no Admin panel page was added
  (the contract lists only Goods and Referrals as new admin pages for this program).
- `combinedLevel` is refreshed on every per-pair recompute and on the admin rebuild, but **not** when
  a player's level changes without a game (manual admin adjustment). It is display-only and the sort
  is a secondary mode; the rebuild endpoint fixes it.
