## 1. Done

### 1.1 `/live`

`Backend/src/services/telegram/commands/live.command.ts` — **new**, written against
`games.command.ts` (the only existing command that works in both private and group chats).

- City resolution matches `/games`: `City.telegramGroupId` in a group, `user.currentCityId`
  privately. No city → the localized "set your city" line.
- Calls `listLiveGames({ cityId, viewerUserId, limit: 5 })` **in process**. The bot never HTTP
  round-trips to its own API, and calling the service is also what guarantees `/live` obeys exactly
  the same privacy gate as the in-app rail.
- Format: `🔴 Live now in {city}` header, up to five blocks
  (`club · court` / `names  \`6-4 3-2\`  names` / `_Started 23 min ago_`), then
  `_Updated just now · /live to refresh_`. Empty state:
  "Nothing live right now. /games shows what's coming up."
- Scores are monospace (backtick code spans). Player names truncate at 12 characters including the
  ellipsis, trailing space trimmed first.
- One **Watch** URL button per block, carrying a freshly minted `signLiveSpectatorToken`, so the
  link opens the board in a signed-out browser.
- Exported pure pieces for testing: `buildLiveMessage`, `escapeLiveMarkdown`, `truncateName`,
  `startedLabel`, `buildWatchUrl`, `LIVE_COMMAND_MAX_GAMES`, `LIVE_NAME_MAX_CHARS`.

**Markdown safety.** Everything user-supplied goes through `escapeLiveMarkdown` = the existing
`escapeMarkdown` **plus** the backtick. The backtick matters here and nowhere else in the bot: it
delimits the score spans, and Telegram's legacy Markdown has no backslash escape for it, so it is
swapped for the look-alike modifier letter `ˋ`.

**Localhost.** Telegram rejects inline URL buttons pointing at loopback hosts.
`buildMessageWithButtons`'s localhost branch keeps only the *first* URL button, which would drop
four of five Watch links, so `/live` appends all of them as inline Markdown links instead.

### 1.2 `/play`

`Backend/src/services/telegram/commands/play.command.ts` — **new**.

Private flow, editing **one** message in place at every step:

1. "When do you want to play? 🎾" + one row **Today · Tomorrow · {Weekday}**, where the third label
   is the real weekday name of `now + 2 days` **in the city timezone**, resolved from the existing
   `date.shortDay.*` keys.
2. `{day} · what time?` + 2×2 **Anytime · Morning / Afternoon · Evening** + **← Back**.
3. The confirmation block — `✅ You're looking to play` / `🎾 {sport} · {city}` / `📅 {when}` /
   the "we'll message you" line — with **Open in app** and **Stop looking**.

- An existing OPEN intent short-circuits to that same confirmation block, so the one-OPEN-intent
  rule is honoured by *showing* rather than duplicating.
- **Stop looking** cancels and edits to "Stopped looking" + **Look again**; **Look again** returns
  to step 1 in the same message.
- Unlinked users get `generateLoginLink(ctx)` — the standard login-link message from
  `loginMessage.service.ts`.
- No home city or no chosen primary sport → "Set your city in the app first." with an **Open
  profile** deep link. Note `primarySportIsSet`, not `primarySport`, is the signal: the column is
  non-nullable and defaults to `PADEL`.

Group flow:

- Posts `🎾 {name} is looking to play {when} in {city}` with **I'm in too** and **Open app**.
- Rate limited to one post per user per 6 h per group, `Backend/src/services/telegram/playGroupPostLimit.ts`:
  Redis `SET NX PX` with a bounded in-process fallback. A storage error fails **open** — a rare
  duplicate post beats `/play` dying in every group.
- A poster with no OPEN intent gets one created for *today, any time*. `/play` in a group is itself
  the request to play and a group has no room for a wizard; they can narrow it in the app or with
  `/play` in DM.

**No server-side wizard state.** Every step carries what it needs in the callback data, so a bot
restart between two taps cannot strand a user mid-flow.

All intents go through `PlayIntentService.createOrReplace(userId, { cityId, sport, dayOffsets |
dateKeys, timeOfDays })`, which gives the bot the app's rules for free: date keys resolved in the
**city** timezone, the expiry window, the one-OPEN-intent-per-city/sport rule, and every downstream
queue. `/play` never writes `PlayIntent` directly.

### 1.3 `pi:` callbacks

`Backend/src/services/telegram/handlers/callback.handler.ts` — branch added **immediately after the
`sg:` branch** (my assigned anchor).

| Shape | Effect |
|---|---|
| `pi:d:<0..2>` | edit to the time keyboard |
| `pi:back` | edit back to the day keyboard |
| `pi:t:<any\|am\|pm\|eve>:<0..2>` | create the intent, edit to the confirmation |
| `pi:cancel` | cancel, edit to "Stopped looking" + **Look again** |
| `pi:again` | edit back to the day keyboard |
| `pi:join:<intentId>` | mirror the poster's window into an intent for the tapper, confirm by DM |

- Parsing is `parsePlayCallback(data)`, which returns `null` for anything malformed so the handler
  answers the query instead of throwing at the user. Every branch answers the callback query, so a
  button never spins.
- `pi:join` uses the **tapper's** city and sport; date keys the tapper can no longer reach are
  dropped by `resolveDateKeys`. A failed DM (the tapper never opened a chat with the bot) is logged
  and swallowed — the intent is still created and the callback toast still confirms.
- `pi:cancel` catches the "no open intent" error: the message must stop claiming the user is
  looking even when the intent is already gone.

The registration regex already contained `pi` (wave-2 backend scaffold), so `bot.service.ts` needed
no regex change.

### 1.4 Command registration, menu and rate limit

`Backend/src/services/telegram/bot.service.ts`

```ts
this.bot.command('play', requireUser, syncTelegramProfile, requireChat, rateLimitChat(), handlePlayCommand);
this.bot.command('live', requireUser, syncTelegramProfile, requireChat, rateLimitChat(), handleLiveCommand);
…
void registerBotCommandMenu(this.bot);
```

`Backend/src/services/telegram/middleware.ts` — **new** `rateLimitChat(max = 10)` plus the testable
`chatRateLimitAllows(chatKey, max, now, windowMs)` and `resetChatRateLimitForTests()`. Fixed
one-minute window keyed by chat id, pruned on every call so the map cannot grow without bound.
Overflow is dropped silently rather than answered.

`Backend/src/services/telegram/botCommandMenu.ts` — **new**. There was **no `setMyCommands` call
anywhere in the repo**; this adds one, called once at startup with a default English list and then
one localized list per bot language. Because `setMyCommands` **replaces** the whole list for a
scope, `BOT_MENU_COMMANDS` registers *every* command the bot handles (`play`, `live`, `games`,
`my`, `login`, `auth`, `start`) — adding a command to the bot without adding it here makes it
vanish from the "/" menu. Failures are logged and swallowed.

### 1.5 Copy

`Backend/src/services/live/liveCopy.ts` — `liveT(key, lang, params)`, 33 keys × **11 bot
languages** (`en ru sr es cs ar zh id hi th ja`), covering all of `/live`, all of `/play` and the
menu descriptions. Same contract as `t(key, lang)`: unknown language → English, unknown key → the
key. Placeholders are `{name}`-style, matching `seriesT`.

Day and time-of-day labels are **not** duplicated: `playIntent.today` / `.tomorrow` / `.morning` /
`.afternoon` / `.evening` and `date.shortDay.*` already exist in `utils/translations.ts` for all 11
languages and are reused verbatim.

Language resolution is `getUserLanguage(user.language, ctx.from?.language_code)` everywhere.

## 2. Contract deltas

1. **`pi:t:<slot>` became `pi:t:<slot>:<dayOffset>`, and `pi:back` was added.** CONTRACT §5.3 lists
   `pi:d:<offset>` / `pi:t:<slot>` / `pi:cancel` / `pi:again` / `pi:join:<intentId>`. With no
   server-side wizard state, the day chosen in step 1 has to travel into step 2's buttons, and the
   PRD's **← Back** button needs a token of its own. The prefix is unchanged, so the registration
   regex is unaffected.
2. **`/live` is legacy `parse_mode: 'Markdown'`, not the HTML produced by
   `shared/telegramMarkdown.ts`.** That module converts LLM Markdown to Telegram **HTML** and
   deliberately does not unescape backslashes — feeding it `escapeMarkdown`'s output would print
   literal backslashes in player names. `/games`, the command PRD 356 says to follow, is legacy
   Markdown, so `/live` matches it, with `escapeLiveMarkdown` covering the backtick that the
   monospace score spans introduce. The requirement that actually matters — valid, escaped output
   in every locale — is met and tested.
3. **Group `/play` creates a default intent when the poster has none.** The PRD's group card shows
   a day and a time ("tomorrow evening") but a group gives no room to ask. Today + anytime is the
   widest honest reading of `/play`.
4. **"Open in app" points at `${frontendUrl}/?playIntentOpen=1`** — CONTRACT §7.5's documented
   deep-link param for the play-intent compose sheet (owned by PRD 350). If that PRD does not land,
   the param is inert and the button still opens the app.
5. **Backend copy lives in a namespaced module**, not `utils/translations.ts` — same reasoning and
   same precedent as PRD 345's `gameSeriesCopy.ts`.

## 4. Known gaps

1. **No `tsc` / lint / test run.** Highest-risk spots: the discriminated-union narrowing of
   `parsePlayCallback`'s result inside the `callback.handler.ts` if-chain, and the
   `PlayIntentService.createOrReplace` return type flowing into `summaryFromIntent`.
2. **No test that drives the real `pi:` branches end to end.** `parsePlayCallback`, the keyboards,
   the confirmation text and the group post are all covered, and `handlePlayCommand`'s four
   branches are covered with a stubbed prisma — but the callback handler itself would need a much
   larger prisma and `PlayIntentService` fake. The message-edit *payloads* are covered through the
   builders they call; the wiring is UI-test-plan §25.2.
3. **`rateLimitChat` is in-process.** Correct for a single long-polling bot; it would need Redis if
   the bot is ever horizontally scaled. Noted on the function.
4. **Group `/play` cannot send an OTP.** A group member who is not linked gets the city guidance
   rather than a login link, because posting an OTP into a group chat would be a security bug.
   The PRD does not specify this branch.
5. **`/live` in a group is not personalised** — no "You" tag, no followed-season ordering, since
   there is no viewer. Intentional.
