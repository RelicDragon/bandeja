## 2. Contract deltas

### 2.1 `/welcome` **is** an offline-gate exception (CONTRACT §7.5 says "no")

The contract's route table marks `/welcome` as having no offline-gate exception. The PRD's
"Resume and edge cases" section is explicit that the frame must show the existing `OfflineBanner`
and that steps needing the server queue and continue. Those cannot both be true: without the
exemption, `App.tsx` renders `NoInternetScreen` instead of the route, so an offline new user — who
is *sent* to `/welcome` by the gate — is locked out of the app entirely.

I added `/welcome` to the exemption list in `App.tsx`. The app-level `OfflineBanner` already
renders above every route, so no new banner was needed. **Flagging this because it contradicts the
contract table.**

### 2.2 One new optional prop on `SportQuestionnaireContent`

`hideResultSlide?: boolean` (default `false`). The PRD demands onboarding's own result screen
(display scale + count-up + "You can adjust this any time in Profile."), while the shared
questionnaire renders its own congratulations slide with a "Go to app" button. Without the prop the
user confirms twice. The prop skips the internal slide and hands the completed user straight to
`onCompleted`. Every existing call site is unchanged in behaviour.

### 2.3 There is no frontend event-logging path

CONTRACT/PRD say to emit the three analytics events "through the existing event logging path".
There isn't one — `Frontend/src` has no `logEvent`, `trackEvent` or analytics client of any kind
(grepped). `onboardingAnalytics.ts` dispatches a `window` `CustomEvent` named `bandeja:analytics`
and documents itself as the seam. When a real sink lands, it listens for that event and no call
site changes.

### 2.4 `permissionService` does not cover push

The PRD says the notification prompt goes "through the existing `PermissionModalProvider` /
`permissionService` path". That service only models `'photos' | 'camera'`; push registration goes
through `pushNotificationService.ensureTokenSentToBackend({ requestPermission: true })`, which is
what `App.tsx` already uses and what I call. `PermissionModalProvider` was left alone.

### 2.5 `GET /users/suggested` also excludes people you already follow

The PRD says "excluding blocked users and the viewer". Suggesting someone you already follow makes
the step useless, so already-followed users are excluded too, and the follow state starts empty.

### 2.6 The suggestion list has a fallback

The PRD implies 6–8 rows. A brand-new city has no finished games, which would leave the step
permanently empty for exactly the users who need it. Ranked rows are topped up with active city
players who have the sport enabled, reported honestly as `gamesInWindow: 0` and always sorted
behind real ranked rows.

### 2.7 A pending deep link beats the closing choice

PRD: "Deep-link pending path (`deepLinkStore`) is honored after the last step." When the user both
followed a deep link *and* picked a closing card, the deep link wins — that is the screen they
asked for first, and the alternative is silently swallowing it. Documented in the domain delta.

## 4. Known gaps

1. **The step slide is an enter-only animation.** Each step renders its own `OnboardingFrame`, so
   the outgoing step unmounts with its `AnimatePresence`; what the user sees is the incoming step
   sliding + fading in at 260 ms / 24 px, direction- and RTL-correct. A true cross-fade would mean
   hoisting `AnimatePresence` above the frame, which would also animate the progress bar — the one
   thing that must stay put. Deliberate.
2. **Frontend component tests are SSR-only.** The repo has no `@testing-library/react` and no
   jsdom-based interaction harness, so the interactive rules are tested as pure functions
   (`sportSelection`, `followSelection`, `nameValidation`, `onboardingGate`, `onboardingSteps`)
   plus one `renderToStaticMarkup` test of the frame. Real click-through coverage is the Playwright
   spec.
3. **No test asserts the long-press timing.** `LONG_PRESS_MS` behaviour is manual (§25.4.5); the
   state transition it produces is covered by `sportSelection.test.ts`.
4. **`onboarding_*` events go nowhere yet** — see §2.3.
5. **The `?step=sport` flow does not call `POST .../complete`** (the account is already completed).
   It settles the cached status optimistically instead. If the sport write succeeded but the user
   killed the app before the cache was read, the next launch re-derives `needsSportStep` from the
   server and correctly allows through.
6. **`GET /users/suggested` runs two `groupBy` queries** (60-day ranking + 30-day display count).
   Both are indexed on the `GameParticipant`/`Game` relation, and the endpoint is called once per
   onboarding, so this was not optimised further.
7. **City-stats cache is per node.** An hour-stale player count on one node is acceptable for a
   social-proof line; it is never used for a permission decision.
8. **I could not run anything.** No typecheck, no lint, no test. The riskiest spots are listed in
   §6.
