## 0. The product principle, and where it is enforced

Confirmation is a courtesy signal, never a contract. Three independent guards, deliberately
layered so that removing one still fails the build:

1. **Runtime** — `assertAttendanceUpdateIsSafe` in `attendanceRules.ts`. Every participant write
   goes through `buildAnswerUpdate` / `buildNoShowNoteUpdate` / `buildNoShowUndoUpdate`, each of
   which runs the guard against an explicit allow-list.
2. **Source scan** — `attendanceRules.test.ts` reads every file under
   `Backend/src/services/gameAttendance/` (comments stripped) and fails if any of them mentions
   `ratingUncertainty`, `reliability`, `LevelChangeEvent`, `approvedAtLevel`, `queuePosition`,
   `removeParticipant`, `leaveGame`, writes the `User` row, or performs a `gameParticipant.update`
   that does not use a guarded builder.
3. **Real database** — `gameAttendance.invariants.integration.test.ts` snapshots the whole roster,
   both `User` rows, both `UserSportProfile` rows, the `Game` row and the `LevelChangeEvent` count
   before and after **every** attendance operation and asserts that only the four attendance
   columns and the two informational counters moved.

The frontend half: `patchViewerAnswer` (the optimistic write) is isolated in a pure module and
unit-tested to prove it touches only the viewer's own row, and `AttendanceCard.test.tsx` asserts
the required caption *"Just so the organizer knows. Your seat is yours either way."* is present
in both the ask and the answered state.

## 2. Contract deltas

1. **Plural suffixes.** CONTRACT §8.3 asks for i18next `_one`/`_other` plurals where a count is
   interpolated, but `localeParity.test.ts` asserts an **exactly identical key set** across
   locales — which is incompatible with `ru` / `cs` / `sr` / `ar` needing `_few` / `_many` /
   `_zero` / `_two`. Adding only `_one`/`_other` would silently mis-resolve for those languages.
   I resolved it by **writing copy that does not need grammatical agreement**: "Nudge again in
   {{hours}} h", "Nudge sent", "{{month}} — attended {{attended}}, missed {{noShow}}". No plural
   suffixes anywhere in `attendance.json`. If the programme wants real plurals, the parity test
   needs a plural-aware key-set rule first.
2. **Two keys removed rather than allowlisted.** `stat.percent` (`"{{rate}}%"`) and
   `card.fraction` (`"{{confirmed}}/{{total}}"`) would have been byte-identical in every locale
   and failed parity. They are now formatted in code with `Intl.NumberFormat`, which is more
   correct anyway (Arabic-Indic digits, RTL percent placement). I did **not** touch
   `PARITY_IDENTICAL_ALLOWLIST`.
3. **`errors.attendance.*` stays a backend-only key space.** The `errors` i18n namespace is not
   mine, so `attendanceErrorKey()` maps each backend code onto a key in my own `attendance.errors.*`
   namespace at the call site (the same pattern `utils/genderJoinGate.ts` already uses). The
   backend keys exist in `Backend/src/utils/translations.ts` for push/Telegram surfaces.
4. **`canEditGameIncludingArchived`, not `canEditGame`.** The PRD says `canEditGame`; that
   middleware rejects ARCHIVED games, and a no-show is noted *after* the game, when it may already
   be archived. The `IncludingArchived` variant has the same role set and the same parent-game
   permission (which is what gives a league **season** owner/admin authority over a fixture).
5. **`NotificationData.attendanceUnsureActionToken` added.** The wave-2 scaffold provided one
   `attendanceActionToken`, but two shade actions need two signed tokens.
6. **No-show UI lives in the attendance card, not the roster overflow, after the game.**
   `GameParticipants` is only rendered while `resultsStatus === 'NONE'`; a FINAL game shows
   `ResultsRosterCard` instead. Rather than edit that shared component, the organizer's
   after-the-game roster (avatar + dot + tag + overflow) is rendered by `AttendanceNoShowPanel`
   inside the attendance card, which covers FINISHED, ARCHIVED and FINAL uniformly. The overflow
   *is* also present on the pre-FINAL roster rows via `GameParticipants`.
7. **Socket event name.** The PRD says `game:attendance-updated`; per CONTRACT §1/§6 the
   kebab-case `game-attendance-updated` is used.

## 4. Known gaps

1. **iOS notification category is not registered in the app.** `resolveApnsNotificationCategory`
   already yields `GAME_REMINDER` as the APNs category for the reminder (it derives from the
   notification type), and the payload carries `confirmActionTitle` / `unsureActionTitle` /
   both tokens. But **there is no `UNNotificationCategory` registration anywhere in
   `Frontend/ios/App`** — I grepped: `setNotificationCategories`, `UNNotificationAction` and
   `categoryIdentifier` appear nowhere, so the existing INVITE accept/decline shade actions are
   Android-only today. Wiring a category + two `UNNotificationAction`s + a delegate branch that
   POSTs `/api/push/invite-action` is a genuine native change and is out of proportion to
   "a small addition". **Remaining work:** register `GAME_REMINDER` with
   `confirm` / `unsure` actions in `BandejaPushNotificationDelegate.swift` and handle the
   response by calling the unauthenticated action endpoint with `attendanceActionToken` /
   `attendanceUnsureActionToken`.
2. **Android shade actions need a Java handler.** The backend sets
   `nativeHandler = 'attendance_actions'`, but `ChatReplyMessagingService.java` only branches on
   `invite_actions` / `play_intent_actions`. **Remaining work:** an `AttendancePushData` +
   `AttendanceNotificationHelper` + `AttendanceActionReceiver` trio modelled 1:1 on the existing
   `InvitePushData` / `InviteNotificationHelper` / `InviteActionReceiver`, posting the token to
   `/api/push/invite-action`. Everything the Java side needs is already on the data map.
   Until then, the Telegram buttons and the in-app card work and the push simply opens the game.
3. **Watch Confirm button.** The JS envelope side is done (`CachedNextGameDTO.attendance`), the
   Swift model carries the field and `needsAttendanceAnswer` encodes the 24 h rule. The Watch app
   has **no networking layer of its own** — it renders a cached envelope — so an actual Confirm
   button needs a WatchConnectivity message back to the phone plus a phone-side handler.
   **Remaining work:** a `WatchSessionManager` message kind `attendance.answer` and the
   corresponding button in the Next Game view.
4. **The organizer legend is a toast, not a popover.** Long-press / right-click on a dot shows the
   legend as a toast; the PRD says "legend on long-press". A true long-press gesture (touch timer)
   was not added — `onContextMenu` covers desktop right-click and Android long-press, but not iOS
   Safari. The organizer caption under the progress pill carries the same information
   unconditionally, so no information is only available through the gesture.
5. **`attendanceSummary` on Find cards.** The enricher is registered and returns `null` for games
   the viewer is not PLAYING in, so the stack appears on My-tab/Home cards for the viewer's own
   games. It will also appear on a Find card for a game the viewer has already joined — which is
   what "viewer's own games only" means, but worth a visual check.
6. **Integration-test teardown may leak rows.** `gameAttendance.invariants.integration.test.ts`
   deletes its own game/users/city, but `ChatSyncEvent` rows created by the no-show system message
   are not deleted and could block the `game.delete` (it is wrapped in `.catch`, so the test still
   passes — it just leaves a row behind in `padelpulse_dev`).
7. **No test for the reminder-filtering logic itself.** The 2 h filter is three lines inside a
   private scheduler method with no seam; it is covered by UI test case 18.5.3 (@manual).
