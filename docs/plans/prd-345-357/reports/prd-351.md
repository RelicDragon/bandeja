### 1.3 Backend — attribution pipeline (the correctness core)

- `linkToApp.attributionParse.ts` — `LinkToAppAttributionInput` gains `ref: string | null`, parsed
  through `normalizeReferralCode` from `merged.ref` (so it works from the query, the body, **and**
  the nested `attribution` snapshot the axios interceptor sends). `attributionHasSignal` now counts
  a bare `ref`, which is what makes `/games/:id?ref=` work — that URL carries no `aid` and no UTM.
- `linkToApp.service.ts` — new private `attachReferrerFromAttribution`, called from
  `applyAuthAttribution` after the attribution upsert **and** on the `attachOnly` early-return path
  (a user can open an invite link after signing up). It dynamically imports the referral service,
  never throws, and passes the attribution id through.
- `linkToApp.service.ts` — `recordLinkToAppEvent` also stamps `referrerUserId` on the attribution
  row at **view** time. Without that, a link that was opened and never signed up could never show
  as a pending "Invited" row: `referrerUserId` written only at conversion always arrives together
  with `convertedUserId`, so the pending state would have been unreachable. Same `null`-guarded
  `updateMany`, so a second scan carrying a different code cannot steal the row.
- **First touch is enforced by the database, not by an `if`.** `attachReferrer` writes
  `User.referredByUserId` via `updateMany({ where: { id, referredByUserId: null } })` and
  `LinkToAppAttribution.referrerUserId` via the same `null`-guarded `updateMany`. Two concurrent
  attaches cannot both win. The 7-day window is enforced here too, not only on manual entry.

## 2. Contract deltas

1. **Manual entry is `POST /referrals/me/code`, not `POST /users/me/referral-code`.** `/users` is
   owned by `user.routes.ts` plus the pre-created onboarding/recap routers, and CONTRACT §5.5
   forbids feature agents from touching `routes/index.ts`. The endpoint lives on the router this
   PRD owns; semantics are identical. Documented in the route file header and in `api/referral.ts`.
2. **Error keys are `referral.errors.*`, not `errors.referral.*`.** The house convention is
   `errors.<domain>.<key>`, but `errors.json` is a shared file this agent does not own, and the
   frontend renders an unresolved key verbatim — the user would literally read
   `errors.referral.selfCode`. Putting them inside this PRD's own namespace means they resolve
   today with no cross-file edit. If the orchestrator prefers the house convention, the change is
   mechanical: move the six `errors` entries from `referral.json` into `errors.json` under
   `referral`, and flip the prefix in `referralAbuse.ts#referralAbuseErrorKey`,
   `referral.service.ts`, `referralCodeValidation.ts#referralCodeErrorKey` and the two controllers.
3. **`menu.invite` was added to `Backend/src/services/live/liveCopy.ts`**, which belongs to
   PRD 356. `BOT_MENU_COMMANDS.descriptionKey` is typed `LiveCopyKey`, so registering `/invite` in
   the command menu required either one additive key in that file or a discriminated union that
   would have rewritten all seven existing entries. I took the one-key option: purely additive,
   union member + 11 bundle entries, no existing line changed.
4. **`ReferralAbuseReason` has a seventh value, `UNKNOWN`.** Defensive branch for "one of the two
   accounts could not be loaded"; it maps to `referral.errors.invalidCode`. Without it that branch
   had to reuse `SELF`, which would have told a user "you can't use your own code" about somebody
   else's account.
5. **`NotificationData.referralReward?: string`** added to
   `Backend/src/types/notifications.types.ts` (one optional field, same style as the other PRDs'
   additions), so the app can tell a referral `TRANSACTION` push from any other one.
6. **`TRANSACTION` push taps now navigate.** That type had no case in `handleNotificationTap` at
   all, so every coin push opened the app on whatever was last on screen. Adding the case is
   required by the PRD's reward moment and is an improvement for the other coin pushes too.
7. **The 7-day window applies to link capture, not only manual entry.** The PRD scopes it to manual
   entry. Without it on the link path, a three-year-old account could open a fresh referral link
   and become somebody's referral — exactly the loop the cap exists to prevent.
8. **`InviteFriendToGameButton` lives in the share *dialog*, not a new sheet.** The PRD says
   "the existing `ShareModal` gets an option"; the option is opt-in via `showGameInvite` because
   the same modal is reused for player profiles, where a referral link is meaningless.

## 4. Known gaps

1. **The 50-invite cap has no integration test.** It would need 50 real `User` rows plus 50
   `ReferralReward` rows to exercise `checkReferralEligibility` returning `CAP_REACHED`. The rule
   itself (`isReferralCapReached`) and the frontend's cap presentation are unit-tested, and the
   count query (`countRewardedReferrals`, revoked rows excluded) is exercised by the revoke case.
2. **`SHARED_TELEGRAM` and `SHARED_PHONE` are unit-tested only.** `User.telegramId` and
   `User.phone` are both `@unique`, so a genuine duplicate cannot be created in a DB test — the
   rules cover the window between an account merge and a re-link. The integration test asserts
   `SHARED_DEVICE` and `SHARED_PUSH_TOKEN`, which *can* be reproduced, and says so in a comment.
3. **The `WalletModal` highlight is not covered by a mounted component test.** Mounting it needs
   the Radix dialog, `transactionsApi`, `WalletOwedSections` and the sport-level context. The two
   pieces with logic in them — `walletHighlightStore` and `walletReferralRow` — are unit-tested,
   and the visual is covered by UI-test-plan case NN.7.2/NN.7.4.
4. **The landing-page chip is effectively iOS-only in practice.** Non-iOS visitors are redirected
   after ~500 ms, so the chip may only flash. That is the page's pre-existing behaviour; the
   redirect target still carries `ref`, which is the part that matters.
5. **`ReferralCodeField` in `account` mode applies the code as soon as it validates**, rather than
   behind a separate "Apply" button. The PRD only specifies inline validation with a green check;
   auto-apply is the natural reading for a field that is already debounced, but it is a judgement
   call and easy to reverse.
6. **No Telegram test for `/invite`.** The bot commands have no test harness in this repo
   (`live.command.test.ts` and `play.command.test.ts` test pure builders, and `/invite` has none —
   its message is three `referralT` calls and a link).
7. **Revoke does not claw coins back.** Deliberate and documented; the PRD scopes revoke to the
   referral record.
