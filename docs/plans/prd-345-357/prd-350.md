# PRD 350: PRD: Guided first-run onboarding

## Problem Statement

New users land on Home with three competing banners: city prompt, sport questionnaire, and gender prompt on Find. `/welcome` is a stub redirect. Users with no enabled sport are bounced to Profile. There is no ordered first-run, no follow suggestions, and no immediate action that gets a new player into a game.

## Solution

A real onboarding flow at `/welcome` shown once after registration: sport selection, questionnaire, city confirmation, follow suggestions, and a first action (post a play intent or browse Find). Each step reuses the existing component and API. Progress is saved per step so an interrupted flow resumes.

## User Stories

1. As a new user, I want a short guided flow after signing up, so that I know what to do first.
2. As a new user, I want to pick my sport(s) first, so that the rest of the app makes sense.
3. As a new user, I want the level questionnaire inline, so that I am not asked again on Home.
4. As a new user, I want my city auto-detected and confirmable, so that Find is not empty.
5. As a new user, I want suggested players to follow (same city, same sport, active), so that Home is not lonely.
6. As a new user, I want a final step offering "I want to play soon" (play intent) or "Browse games", so that I take a real action.
7. As a new user, I want to skip any step, so that the flow never blocks me.
8. As a returning user, I want to never see the flow again unless I have no enabled sport.
9. As a user who quits mid-flow, I want to resume at the same step.
10. As a Telegram-linked or SSO user, I want prefilled name/avatar respected, so that I do not re-enter them.
11. As a developer agent, I want the flow to be a sequence of existing components, not new forms.
12. As a new user, I want to set my name and photo in the flow if SSO did not provide them, so that I am not anonymous in games.
13. As a new user, I want to allow notifications at the moment I understand why, so that I do not reflexively decline.

## UX / UI Design

### Structure
Six full-screen steps in a standalone route, each with the same frame: a thin **progress bar** at the top (sky fill, springs between steps), a **Skip** text button top-right where allowed, a large headline, one interaction, and a single primary button pinned above the keyboard inset. Steps slide horizontally (260 ms, 24 px offset + fade); back gesture returns one step.

1. **Welcome**: sport mascot of the default app icon on a soft radial gradient, headline "Let's find you a game", subline "Two minutes to set you up." Primary **Start**. Under it, the number of players in the detected city if available ("2,400 players in Belgrade"), which sets social proof early.
2. **Sport**: a grid of six sport tiles (icon + name) using the existing sport registry art; tap to select multiple, the first tap sets primary with a small "Primary" tag that can be moved by long-press or a **Make primary** action. Primary button **Continue** enabled after one selection.
3. **Your level**: the existing per-sport questionnaire rendered inside the frame with the same question cards; result screen shows the estimated level on the sport's display scale (e.g., Playtomic 3.5) with a count-up and a one-line explanation "You can adjust this any time in Profile." Skip = level unset (existing questionnaire prompt remains on Home).
4. **Your city**: auto-detected city card with a map thumbnail (`ClubMiniMap` style) and "Is this right?" **Yes** / **Change** (opens `CityModal` content inline). Helper "We show games and players from your city."
5. **People to follow**: a list of 6–8 suggested players as rows (avatar, name with premium treatment if applicable, level badge, "12 games this month"), each with a **Follow** pill that flips to **Following** with a 200 ms scale. **Follow all** text action at top. Skip allowed.
6. **Notifications and first move**: a short card explaining the three things we notify about (invites, reminders, spots) with a **Turn on notifications** primary button that triggers the native permission prompt; then the closing choice as two large cards: **I want to play soon** (opens the play-intent create sheet on Home after finishing) and **Browse games** (lands on Find). Finish shows a brief full-screen "You're set" with the mascot doing a 600 ms bounce, then routes.

### Name and photo (conditional)
- Inserted after Sport when the account has no display name or avatar: name field (keyboard-aware, validation inline) and an avatar picker using the existing crop modal. Skip allowed for photo, not for name.

### Resume and edge cases
- Returning mid-flow lands on the saved step with the progress bar already filled.
- No network: the frame shows the existing `OfflineBanner`; steps that need the server (questionnaire submit, follows) queue and continue.
- Users with no enabled sport but completed onboarding: the app routes them to `/welcome` step 2 only, with the headline "Pick a sport to continue".
- Deep-link pending path (`deepLinkStore`) is honored after the last step.

### Visual language
- One accent per step (sport color for step 2, sky elsewhere), lots of whitespace, illustrations from the existing mascot set, no stock art. Dark mode uses the same gradients at lower luminance. Premium members see the gold tiger variant only on the final screen.

### Accessibility
- Every step is a landmark with the headline as `h1`; progress bar exposes "Step 3 of 6"; tiles are toggle buttons; the flow works fully with a keyboard on web.

## Implementation Decisions

- Route `/welcome` becomes a standalone protected page `OnboardingPage` (replace the `Navigate` stub). Steps as components under `Frontend/src/components/onboarding/`, reusing `sportQuestionnaire`, `CityModal` content, `AvatarCropModal`, and the play-intent create sheet.
- Gate: `User.onboardingCompletedAt` nullable + `onboardingStep` string. `ProtectedRoute` routes users with null completion to `/welcome`; the migration backfills existing accounts as completed. Users with no enabled sport and completed onboarding go to `/welcome?step=sport`.
- Progress: `PATCH /users/me/onboarding` `{ step }` after each step; `POST /users/me/onboarding/complete` at the end.
- Follow suggestions: `GET /users/suggested?cityId&sport&limit` ranked by finished games in the last 60 days, excluding blocked users and the viewer; follow uses `/favorites/users`.
- City count for social proof: `GET /cities/:id/stats` (player count, cached 1 h).
- Notification permission uses the existing `PermissionModalProvider` flow on native; web shows the push opt-in only when supported.
- First action: play intent uses `PlayIntentProvider` with `?playIntentOpen=1` on Home; browse navigates to `/find`.
- Home banners remain for skipped steps.
- i18n: new `onboarding` namespace in all 11 locales.
- Analytics: emit `onboarding_step_viewed/completed/skipped` through the existing event logging path.

## Testing Decisions

- Route gating tests for the user states (new, resumed, completed, no-sport).
- Step resume test; deep-link preservation test.
- Suggested users query test (city, sport, blocked exclusion, ranking).
- FE: each step's primary enablement, skip rules, name validation, follow toggle.
- Playwright happy path (register → onboarding → Home) mirroring existing auth e2e.
- UI test plan section "Onboarding".

## Out of Scope

- Marketing carousels.
- Reworking Register.
- Referral code entry UI (referral PRD adds it to this flow later).

## Design language (shared with every PRD in this set)

- **Mobile first.** Capacitor iOS/Android and mobile browsers are the primary target. Every overlay with an input lays out against the visual viewport via the keyboard contract (`Frontend/src/utils/keyboardLayout.ts`, `body.keyboard-visible`, `--overlay-bottom-inset`). Desktop gets the same components in the split layouts already used by Home/Find.
- **Surfaces.** Bottom sheets (vaul) for actions and detail, Radix dialogs only for destructive confirms, full-screen routes for destinations. Sheets open/close with the existing `[data-state='open'|'closed']` keyframes; all motion gated on `prefers-reduced-motion`.
- **Motion.** Framer Motion 12. Springs for entrance (stiffness 260, damping 24), 180–240 ms fades for state changes, layout animations for list reorders. Never animate more than one hero element at once. Number changes use a count-up tween ≤600 ms.
- **Color.** Tailwind `primary` (sky) for actions, semantic greens/ambers/reds for states, neutral surfaces from `tokens.css`. Premium members keep gold accents where the shell already applies them; new surfaces must read correctly in Light, Dark, Classic, and Premium.
- **Type and density.** One headline per screen, one primary action per sheet, secondary actions as text buttons. Cards keep the `GameCard` rhythm: date tile left, title row, info rows, right rail.
- **Icons.** lucide-react only. No emoji as icons; emoji allowed in copy where playful.
- **Feedback.** `react-hot-toast` for transient confirmations, inline banners for persistent state, skeletons (`GameCardSkeleton` pattern) for loading, `EmptyStateCard` for empties with one clear next action.
- **Accessibility.** 44 px tap targets, 4.5:1 text contrast, roles/labels on every control, arrow-key support on segmented controls, RTL verified for `ar`, all copy in the 11 app locales.
- **Copy.** Plain, second person, verbs first ("Confirm seat", not "Seat confirmation"). No jargon from the schema in user-facing text.
