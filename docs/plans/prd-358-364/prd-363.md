# PRD 363: PRD: Find recovery actions and looking-to-play count

**Status: closed 2026-09-22 — shipped.** Report: `reports/prd-363.md`. Tracked as a PRD document only; no GitHub issue was filed, so this file is the record. Shipped **on** by product decision 2026-09-22, overriding this PRD's "default off"; `FIND_LOOKING_COUNT_ENABLED = false` in Platform Settings is the per-environment switch. Deliberately deferred: the probe-query "which filter blocked you" explanation, and blocked-user filtering inside the count.

## Problem Statement

When Find has nothing to show, it shows an `EmptyStateCard` with a title and a search-off icon. The card supports `description` and `action`, but neither is used. A player who filtered too hard, picked a quiet day, or lives in a sparse city gets a dead end at the exact moment they were ready to play. Separately, the app knows how many people want to play today (play intents in the discovery window) and never says so.

## Solution

Give the empty state a next step and a reason to believe one exists. The card gains up to two actions chosen by context: **Create a game on {day}** (prefilled) and **Clear filters** (only when a non-default filter is active). It gains a one-line description with the number of people looking to play today in the Home city and sport, which links to the court lobby. The same count appears as a caption inside the existing `PlayIntentHomeStrip` on Find. The count is behind an Admin platform setting and hides below three. This PRD deliberately ships without the probe-query "which filter blocked you" explanation; that is a follow-up once these actions have numbers.

## Product principle

A recovery action must be honest and one tap. "Clear filters" clears exactly the filters shown in the panel; "Create" opens the normal flow with only the date set; the count is people, not a promise of a match.

## User Stories

1. As a player on an empty day, I want a one-tap "Create a game on Thursday", so that an empty screen becomes my game.
2. As a player who filtered too hard, I want "Clear filters" right there, so that I do not hunt for the panel.
3. As a player in a sparse city, I want to see "5 people looking to play today", so that I know it is worth posting an intent.
4. As a player who taps that line, I want to land in the court lobby with my intent editor open.
5. As a player under a PRD 358 shortcut, I want the empty title to name the shortcut and the create action to use its day.
6. As an admin, I want to switch the count off per environment without a deploy.
7. As a developer agent, I want the count endpoint to be cheap and cached, not the physics pool.

## UX / UI Design

### Empty state (`AvailableGamesSection` → `EmptyStateCard`)
- **Title**: existing `resolveFindEmptyMessage` result, or the PRD 358 shortcut title when one is active.
- **Description** (one line, muted): *{n} people are looking to play {today | today and tomorrow} in {city}.* Rendered only when the count is ≥ 3 and the flag is on. Tapping the line calls `navigationService.navigateToFind({ playIntentOpen: 1 })`, the existing lobby deep link.
- **Actions** (stacked, full width, max two):
  1. **Create a game on {Thu 18 Sep}** — primary. Calendar view: the selected day. List view: tomorrow. Under a Tonight shortcut: today, 19:00 default in the wizard is untouched (date only).
  2. **Clear filters** — secondary outline, only when any of: entity chips on, club filter, time window not 00:00–24:00, level range not 1–7, available-slots, suitable-rating, no-rating, hide-bar, novice-only (PRD 360), sport ≠ primary. It resets those to defaults, keeps the day and view, and clears any PRD 358 shortcut. Toast: *Filters cleared.*
- When neither action applies (no filters, count hidden), the card shows title + Create only. Never empty of actions.
- Day-load error keeps `FindDayLoadErrorEmpty`; this PRD does not touch it.

### Play-intent strip (`PlayIntentHomeStrip` on Find)
- A caption line under the strip's existing text: *{n} looking today* with the same threshold and flag. Tapping opens the same lobby. No new strip, no badge on the header city chip.

### Copy and locales
- Plural rules for `{n} people` in all 11 locales; "today and tomorrow" variant when the discovery window spans two keys (after 18:00 city time). RTL checked. No "Nobody looking yet" copy anywhere: below three the line is simply absent.

## Implementation Decisions

- Backend: `GET /play-intents/count?cityId&sport` → `{ count, dayKeys }`. Counts distinct users with an intent in `OPEN | MATCHED` for the city and sport whose date key is in `playIntentDiscoveryDateKeys(city.timezone)`, excluding the viewer, excluding users already PLAYING in a game in that window (same rule the pool uses for `inGame`). Reads intents only, no proposal or physics. Cached 60 s in Redis per `(cityId, sport, dayKeysHash)`; `play-intent:invalidate` does not bust it (60 s staleness is fine). Zod query schema reuses `playIntentOptionalScopeQuerySchema`.
- Flag: `PlatformSetting` key `find.lookingCount.enabled` (`'true' | 'false'`, default off). New `GET /api/public/platform-flags` returns an **allow-listed** map (`find.lookingCount.enabled`, and `game.organizerNextActions.enabled` for PRD 364), no auth, 5-minute cache header. Admin sets it through the existing platform-settings admin route. The count endpoint returns `{ count: null }` when the flag is off so the client needs no second call.
- Frontend: `useLookingCount(cityId, sport)` react-query hook, `staleTime` 60 s, enabled only on Find. `usePlatformFlags()` hook, fetched once per session. Empty-state actions in a pure `resolveFindRecoveryActions(state) → { createDay, canClearFilters }` with tests. Clear-filters uses the existing `useGameFilters` reset for the listed keys only.
- Create prefill: `useHeaderStore.getState().setCreateGameInitialDate(day)` then `navigate('/create-game')`, the same call the calendar uses.
- No schema migration (`PlatformSetting` exists). No notification.

## Testing Decisions

- Backend: count excludes viewer, counts distinct users, respects the two-key window after 18:00, returns null when the flag is off, cache hit within 60 s; flags endpoint returns only allow-listed keys.
- Frontend: recovery action resolver matrix (calendar/list, shortcut on/off, each filter kind); empty state renders description only at ≥ 3 with flag on; Clear filters resets exactly the listed keys and clears the shortcut; Create sets the header store date.
- UI test plan rows: empty day → create; filtered-empty → clear; count line visible with a seeded city.

## Out of Scope

- Probe-query filter explanation ("games appear if you widen the level") — follow-up.
- Saved filter alerts (demoted, separate PRD).
- Nearby-city suggestions in the empty state.
- Showing the count on the My tab Play hero or the header chip.
- Any booking action.

## Further Notes

The 60-second cache and the ≥ 3 threshold are the two guardrails against the count looking wrong or discouraging. Keep both until there is data.
