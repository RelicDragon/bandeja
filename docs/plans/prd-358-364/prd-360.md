# PRD 360: PRD: Novices welcome (organizer toggle, card tag, Find filter)

## Problem Statement

A new or low-level player cannot tell which games will welcome them. The level range is a gate, not an invitation: a 2.0–4.0 game may be four regulars who tolerate a beginner, or a group that likes helping people learn. Organizers have no way to say which, and novices either join awkwardly or do not join at all.

## Solution

One explicit organizer choice, **Novices welcome**, saved on the game and shown as a tag wherever the game is listed. It is set in the same settings block as the other toggles in create and in game details, appears in the existing header tag row on cards and on the details header, and can be filtered in the advanced panel. It changes atmosphere, not gates: level range, gender rule, direct-join and queue rules apply unchanged.

## Product principle

The tag is a promise the organizer makes on purpose. It is never inferred from the level range, never auto-set, and never used as a label on a player.

## User Stories

1. As an organizer, I want a "Novices welcome" switch when I create a game and later in game settings, so that I can invite newer players in.
2. As a browsing player, I want the tag on the card and the details header, so that I know before I tap.
3. As a novice, I want to filter Find to games with the tag.
4. As an organizer, I want the switch to lock once results start, like the other settings.
5. As an organizer running a series or repeating a game, I want the choice carried into the next occurrence and into "play again".
6. As an admin, I want to see how many games in a city carry the tag, so that I notice if it stops meaning anything.
7. As a developer agent, I want one boolean column and no derived state.

## UX / UI Design

### Settings toggle
- **Create**: `Frontend/src/components/createGame/GameSettingsSection.tsx`, a `ToggleSwitch` row after "Anyone can invite". Title **Novices welcome**. Hint: *You'll help newer players settle in. The level range still applies.* Default off.
- **Details**: `Frontend/src/components/GameDetails/GameSettings.tsx`, same row style as `afterGameGoToBar`, same optimistic save, error and success treatment. Visible to owner/admin; editable while `resultsStatus === 'NONE'`; locked with the other settings afterwards.
- Entity types: GAME, TOURNAMENT, TRAINING, BAR. Hidden for LEAGUE fixtures, LEAGUE_SEASON, EVENT.

### Tag
- **Cards** (`GameCardHeaderTags`): after the gender tag, same pill height and ring style as the private tag. lucide `Sprout` icon, label **Novices welcome** with `hidden sm:inline` on the text (icon-only on narrow cards, `title` and `sr-only` text always present). Renders only when true. Never a second tag row.
- **Details header** (`GameInfo` format tags): same pill, full label.
- **Chat game cards** and My cards inherit through the shared header tags.

### Filter
- **Advanced panel** (`FiltersPanel`): a switch **Novices welcome only**, grouped with "Available slots". Persisted with the other filters (`filterNoviceFriendly`). Applied in SQL, not as a client residual.
- The filter is not a top-level chip (the entity chip row stays five-up).

### Copy guardrail
- The word "beginner" is not used in UI; "novice" reads the same in most locales and avoids the level-band label `sportRating.beginner`.

## Implementation Decisions

- Schema: `Game.suitableForNovices Boolean @default(false)`. One named migration. Index not needed.
- Backend:
  - `create.service.ts`: accept `data.suitableForNovices ?? false`; force `false` for entity types without the capability.
  - `update.service.ts` whitelist: add `'suitableForNovices'`.
  - `gameResultsLockedFields.ts`: add it to the locked list.
  - Projections: `GAME_DETAIL_GAME_SCALAR_SELECT`, `FIND_CARD_GAME_SELECT`, the My tab game select in `myTabData.service.ts`, and the chat game-card projection if it has its own select.
  - Find: `availableGamesStructuralWhere.ts` gains `noviceOnly?: boolean` (param `noviceOnly=1`), `parseStructuralFiltersFromQuery` parses it, where-builder adds `suitableForNovices: true`. Update the FilterSpec table comment in that file.
  - Series (PRD 345): the series template JSON copies the flag into each generated occurrence; verify `GameSeries.template` builder and add the key.
  - Admin: the games table gains a filter/column for the flag; no new page.
- Shared: `Frontend/shared/entityCapabilities.ts` new flag `hasNoviceTag` (true for GAME, TOURNAMENT, TRAINING, BAR). Create-template parity test unaffected unless a template default is added (do not add one; default is always off).
- Frontend: `Game` type, `useGameFilters` new persisted key, `gamesApi.getAvailableUpcomingGames` / `getAvailableGames` param, `buildDuplicateGameInitialData` copies the flag (PRD 362 relies on it), settings union and `readSetting` default false, header tags, GameInfo tags, FiltersPanel switch.
- i18n: `createGame.suitableForNovices.title/hint`, `games.noviceFriendly`, `games.filterNoviceOnly` in 11 locales.
- No notification, no rating effect, no subscription field.

## Testing Decisions

- Backend: create forces false for EVENT/LEAGUE; update accepts for GAME and rejects after results start (locked-fields test); structural where filters by the flag; projections include it (existing projection tests extended).
- Frontend: settings row saves and locks; create toggle seeds the payload; header tag renders only when true and hides text below `sm`; FiltersPanel switch persists and sends `noviceOnly=1`; duplicate builder copies it.
- Parity: `createTemplates.parity.test.ts` unchanged and green.
- UI test plan rows: set in create, toggle in details, filter on Find, tag on card and header.

## Out of Scope

- Suggesting the toggle from the level range.
- A subscription/alert filter, a push, a badge on organizers, or any label on players.
- A top-level Find chip.

## Further Notes

Guardrail metric: share of newly created games with the tag, per city. If it passes roughly half, the tag has stopped discriminating and the copy should be revisited before adding more surfaces.
