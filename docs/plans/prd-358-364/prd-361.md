# PRD 361: PRD: Played with — recent co-players as the invite Search zero-query state

## Problem Statement

Organizers invite the same people again and again, and each time they type names into the invite modal. The backend already knows who has played with whom: the invite user-search handler computes `gamesTogetherCount` from finished games where both players were PLAYING, and sorts the empty-query list by `UserInteraction.count`. But that empty-query list is "people in this city ordered by how often I tapped them", not "people I actually played with", and the modal gives no hint that the first rows are special.

## Solution

Make the zero-query state of the invite **Search** pane a "Played with" group: up to ten players the viewer has shared finished games with, most recent first, relevant to the game's sport, with the usual row state (already playing, invited, queued). Typing still searches everyone. No new tab, no new modal, no new endpoint shape: the existing search response gains recency and the client groups the top rows under one header.

## Product principle

The list is a memory aid, not a recommendation. It only contains people the viewer has actually played a finished game with, and it says so.

## User Stories

1. As an organizer opening the invite modal, I want to see the people I recently played with before typing, so that inviting a regular is one tap.
2. As an organizer, I want rows to show who is already in this game, invited, or queued, so that I do not invite twice.
3. As an organizer of a tennis game, I want padel-only co-players left out, so that the list is relevant.
4. As a player, I want to appear in someone's list only if we shared a finished game as players, not because I queued or was invited once.
5. As an organizer with no history, I want the modal to look exactly as it does today.
6. As a player who blocked someone, I want them never to appear, and I want never to appear in theirs.
7. As a developer agent, I want the co-play predicate written once and reused by the profile "last played together" line later.

## UX / UI Design

### Search pane, empty query
- Above the existing empty-query list, a group header **Played with** (small caps, muted) and up to ten `PlayerListItem` rows. Below it, a second header **Everyone in {Browse city}** for the existing list, so the boundary is explicit. If the Played-with list is empty, no headers: the pane is unchanged.
- Each row shows the existing stats line plus a short recency caption: *Played together 3 days ago · 5 games*. Caption is one line, muted, wraps in long locales.
- Row state, selection checkbox, multi-select and the send bar are the existing ones (`selectedUserIds`, `expandSelectionToPlayerIds`). No change to how invites are sent.
- **Looking** tab and sport chips unchanged.

### Typing
- First character: headers disappear, the pane becomes today's search. Clearing the query restores the grouped state without a refetch (react-query cache).

### Edge cases
- Game sport filter: co-players whose `sportsEnabled` excludes the game's sport are omitted (existing `sportsEnabled` on the response).
- Team invites (`selectedTeamIds`) unaffected.
- Blocked users excluded both directions (existing block filter in the handler).
- Offline: the pane shows the cached list or today's empty state; no error toast.

### Accessibility and locales
- Group headers are `role="heading"` level 3 inside the list region; the recency caption is part of the row's accessible name. Copy in 11 locales; relative time via the existing i18n date helper.

## Implementation Decisions

- Backend (`Backend/src/controllers/user/social.controller.ts`, the invite search handler): extend the raw co-play query to also return `MAX(g."startTime") AS "lastPlayedTogetherAt"`, keep the predicate exactly `gp1.status = PLAYING AND gp2.status = PLAYING AND g."resultsStatus" = FINAL`, add `AND g."startTime" >= now() - interval '12 months'` and exclude `entityType` in (`LEAGUE_SEASON`, `EVENT`). Expose `lastPlayedTogetherAt` on the response next to `gamesTogetherCount`. When the query is empty, order the result by `lastPlayedTogetherAt DESC NULLS LAST, gamesTogetherCount DESC, interactionCount DESC` and return at least the top ten co-players before city fill. No new route.
- Index check: `GameParticipant(userId, status)` and `Game(resultsStatus, startTime)` are covered by existing indexes; verify with `EXPLAIN` on a large city and add `@@index([userId, status])` on `GameParticipant` only if missing.
- Frontend: `Frontend/src/components/playerInvite/inviteEntries.ts` gains `lastPlayedTogetherAt`; a pure `groupInviteEntries(entries, { query, gameSport })` returns `{ playedWith, everyone }` with the ten-cap and sport rule. `PlayerListModal` renders two headed groups from that. Cache key includes game id, Browse city and sport.
- Documented predicate lives in `docs/domains/social-and-profile.md` ("Co-play"): both PLAYING, results FINAL, 12 months, not LEAGUE_SEASON/EVENT. Queue, invited, guest, trainer and NON_PLAYING never count.
- No schema, no notification.

## Testing Decisions

- Backend: handler test with fixtures — co-player via FINAL game ranks above a high-interaction non-co-player; queued-only and invited-only pairs excluded; 13-month-old game excluded; blocked pair excluded; EVENT excluded; empty query returns ≤10 co-players first.
- Frontend: grouping unit tests (cap, sport filter, empty → no headers); modal test: headers appear only with empty query and non-empty history; typing hides them; selection survives the switch.
- UI test plan rows: open invite on a game with history, invite a Played-with row, type to search.

## Out of Scope

- A third tab, a "usually free" sort, online dots.
- Showing the list anywhere other than the invite modal (profile "last played together" is a later rider).
- Any change to invite delivery.

## Further Notes

`UserInteraction` (tap count) stays as the tiebreaker only. It is not evidence of having played together.
