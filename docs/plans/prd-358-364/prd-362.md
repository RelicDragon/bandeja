# PRD 362: PRD: Play with this group again

**Status: closed 2026-09-22 — shipped.** Report: `reports/prd-362.md`. Tracked as a PRD document only; no GitHub issue was filed, so this file is the record. Two review gaps (trainer badge, client-side blocked-user filtering) were closed during review. Carried forward: `CreateGame` / `GameDetailsShell` are pinned by source assertions with the e2e spec as the behavioural proof, and the invite loop stays sequential and best-effort (pre-existing).

## Problem Statement

After a game finishes there are two ways to set up the next one and neither does the job. **Play again** in the results share card (`GameResultsShareCard`, GAME only, playing participants) opens create with `buildDuplicateGameInitialData`, which copies the **old start time, end time, court id and booked-court flag** and invites **nobody**. **Duplicate** on the shell (`GameActionCard`, `canEdit` and not IN_PROGRESS) does the same for editors. So the organizer picks a new time by hand, fixes a court that is not booked, and re-invites everyone through search. Two entry points, both incomplete.

## Solution

One action after FINAL, **Play with this group again**, as the primary control of the results area. It opens the existing create flow with the format copied, the time and court cleared so a fresh schedule is required, and the previous PLAYING roster preselected as invitees using the create flow's existing `invitedPlayerIds` path. For FINAL games it replaces both Play again and Duplicate. Duplicate stays only on non-FINAL editable games.

## Product principle

Nothing from the old game is treated as still valid: not the time, not the court, not the booking, not attendance, not payments. What carries over is the format and the people, and the people are invited, never seated.

## User Stories

1. As any player who was PLAYING in a finished game, I want one button to start the next one with the same group, so that organizing takes a minute.
2. As that player, I want the create flow to open on the date step with the same format and level range already set, so that I only pick when and where.
3. As that player, I want the previous roster shown as invitees I can remove before sending, so that nobody is invited by accident.
4. As an invitee, I want a normal invite that I accept or decline; never a seat I did not ask for.
5. As an organizer, I want no court, booking, attendance or payment state to leak into the new game.
6. As an organizer who wants this weekly, I want a secondary link to the series flow (PRD 345) after creating.
7. As an editor of an unfinished game, I want Duplicate to keep working as today.
8. As a developer agent, I want the field allow-list for the draft in one tested module.

## UX / UI Design

### Results area (`GameResultsShareCard`, rendered by `GameDetailsShell` after FINAL)
- The existing violet **Play again** button becomes **Play with this group again** (lucide `Users`), full width in the same `max-w-sm` grid. Caption under it: *Pick a new time. We'll invite the same players.*
- Visible to participants who were PLAYING (existing `getGameParticipationState(...).isPlaying`) for GAME, TOURNAMENT, TRAINING and BAR. Hidden for LEAGUE fixtures, LEAGUE_SEASON, EVENT.
- The share card visual and the stories switch stay; they are secondary and sit below.
- The **Duplicate** `GameActionCard` on the shell is not rendered when `resultsStatus === 'FINAL'`. It stays for `NONE` (and is already hidden for `IN_PROGRESS`).

### Create flow (`/create-game`)
- Opens with `initialGameData` from the rematch builder: `timeIsSet` false, no start/end, no court, no booking flags. The wizard lands on the date/time step, then club/court as today.
- The invite step shows the preselected players as removable chips (existing `initialInvitedPlayerIds` handling, which already filters by sport). The creator is never in the list. Trainer of a TRAINING is preselected as trainer invite only if `trainerId` was set and the trainer is not the creator; otherwise the trainer step is empty.
- On create, invites go out through the existing post-create call. Nothing is sent when the draft is abandoned.
- After a successful create from a rematch, the success toast offers a secondary text action **Make it weekly** that opens the existing series creation from this game (PRD 345 entry point). If that entry point requires the game to be the first occurrence, keep the link; otherwise omit rather than build a new path.

### Naming
- The draft name is the old name if it was authored, otherwise empty (existing behaviour). No "(rematch)" suffix.

### Accessibility and locales
- Button label and caption in 11 locales; the caption is part of the button's description. Profile-name gate (`runWithProfileName`) unchanged.

## Implementation Decisions

- `Frontend/src/utils/buildDuplicateGameInitialData.ts` gains a second export `buildRematchGameInitialData(game)`. Allow-list copied: `entityType`, `gameType`, `name`, `description` (authored), `sport`, `clubId` (venue only), `scoringPreset`, `scoringMode`, `playersPerMatch`, `maxParticipants`, `minParticipants`, `minLevel`, `maxLevel`, `isPublic`, `affectsRating`, `anyoneCanInvite`, `resultsByAnyone`, `allowDirectJoin`, `afterGameGoToBar`, `hasFixedTeams`, `genderTeams`, `priceType`, `priceCurrency`, `priceTotal`, `suitableForNovices` (PRD 360), and the format numbers (sets, points, timer, generation, points per win/loss/tie, balls, deuces). Explicitly **not** copied: `courtId`, `startTime`, `endTime`, `timeIsSet`, `hasBookedCourt`, `bookingStatus`, `integrationConfig`, `seriesId`, `trainerId` (moved to invitee logic), `autoFillFromQueue`, `showOnLiveRail` (defaults), any results/attendance/cost/photo/chat fields, `paymentHint`.
- Invitees: `previousRosterInviteeIds(game, viewerId)` = participants with `status === 'PLAYING'`, minus viewer, minus blocked (the create flow re-validates). Passed as `state.invitedPlayerIds` to `/create-game` (existing `CreateGameWrapper` prop).
- Shell: gate the Duplicate card on `game.resultsStatus === 'NONE'`.
- No backend change: create and invite paths are existing. If `POST /games` needs `suitableForNovices`, that is PRD 360.
- Analytics hook: tag the created game with `createdFromGameId` in the create payload **only if** a field already exists; do not add a column for this PRD.

## Testing Decisions

- Unit: rematch builder allow-list snapshot; asserts every excluded key is absent; invitee list excludes viewer and non-PLAYING rows; TRAINING trainer handling.
- Component: share card shows the new label for PLAYING participants across the four entity types and hides it for EVENT/LEAGUE; shell hides Duplicate when FINAL; create wrapper receives `invitedPlayerIds`.
- E2E (existing create-game spec extended): finish a game → play again → date step required → invitee chips present → create → invites exist, no court/booking on the new game.
- UI test plan rows: rematch from FINAL GAME; Duplicate still present on an unfinished game.

## Out of Scope

- Copying courts or triggering any booking (plan §5.7 parked).
- Auto-seating the previous roster.
- A rematch from the card or from chat.
- Series creation changes beyond linking to the existing entry.

## Further Notes

Removing Duplicate for FINAL games is the "replace, do not duplicate" rule (plan §2 rule 11). If usage shows editors miss it, restore it inside the overflow menu rather than as a card.
