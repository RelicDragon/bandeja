# PRD 364: PRD: Organizer next actions

**Status: closed 2026-09-22 — shipped.** Report: `reports/prd-364.md`. Tracked as a PRD document only; no GitHub issue was filed, so this file is the record. Shipped **on** by decision 2026-09-22, overriding this PRD's "ship with the flag off"; `GAME_ORGANIZER_NEXT_ACTIONS_ENABLED = false` is the kill switch. Carried forward: no full shell render test (placement exclusivity plus the `AttendanceCard` prop test stand in), a one-time first-render flash on an environment where an admin turned it off, and the walkthrough GD-NA-01…20 is manual. The 60 frontend `tsc` errors noted in the report are pre-existing and untouched by this PRD.

## Problem Statement

PRDs 346, 347 and 348 gave organizers attendance, open-seat and cost state, and each arrived as its own surface on the game page: `AttendanceOrganizerStrip` ("2 of 4 confirmed" + Nudge) inside `AttendanceCard`, `SpotOpenedGameSection` with its open-spot row and `GameQueuePanel`, `GameLinkedBookingsSection` with a coverage badge, `GameCostCard` with `CostStateChip`, and `WeatherRiskBanner` from PRD 357. An organizer scrolls through all of them to answer one question: what do I still need to do before this game happens?

## Solution

One compact **next actions** block directly under the game header, for owner and admins, that lists at most two things to do right now with a button each, and folds the rest behind a tap. It is a pure view over data the page already has. Two existing organizer surfaces move into it rather than being duplicated: the attendance organizer strip and the open-spot summary row. The queue panel, bookings section, cost card and weather banner stay where they are as the detail views the block links to. No readiness score, no dashboard, nothing on Home.

## Product principle

Every line is a fact with an action. "Nothing to do" renders as nothing. The block never contradicts the sections below it because it is computed from the same props.

## User Stories

1. As an organizer, I want to see "1 player needed · 2 waiting" with a Review button, so that filling the game is the first thing I do.
2. As an organizer, I want "Court not booked" or "Court partly booked" with a button that takes me to the bookings section, so that I do not discover it at the club.
3. As an organizer within 24 h of the game, I want "2 of 4 confirmed" with the existing Nudge and its cooldown, in the same block.
4. As an organizer after the game, I want "2 haven't paid" with a Settle button, and nothing else from before the game.
5. As an admin of the game, I want the same block.
6. As a participant with invite rights, I want only the seats line with an Invite button, and nothing else.
7. As a player who is not an organizer, I want to see no block and no change.
8. As an organizer, I want the block to disappear when everything is done, not turn green.
9. As a developer agent, I want the hint resolution to be a pure function over the detail payload with a fixture-driven test matrix.

## UX / UI Design

### Placement and shape
- `GameDetailsShell`, `variant="game"`, rendered immediately after `GameDetailsHeader` and before `GameInfo`. `Card` with a small heading **Next steps** and a list of one or two rows. Each row: lucide icon, one sentence, one `Button` (text or small filled). Rows are 44 px tall minimum and wrap in long locales.
- Third and later hints collapse behind a **+1 more** text button that expands in place (200 ms height). Never more than four hints exist.
- Not rendered when there are zero hints, when the viewer is not owner/admin (except the invite-rights case), for LEAGUE fixtures, LEAGUE_SEASON, EVENT, or when `status === 'ARCHIVED'`.
- Entrance uses the existing `AnimatedPresencePanel`; reduced motion shows it static.

### Hints, in priority order
| Key | Condition | Sentence | Action |
|---|---|---|---|
| `seats` | `resultsStatus === 'NONE'` and PLAYING < maxParticipants | *{k} player(s) needed* · *{q} waiting* when queue > 0 | **Review queue** (scrolls to `GameQueuePanel`) when queue > 0, else **Invite** (opens `PlayerListModal`) |
| `booking` | `resultsStatus === 'NONE'`, `timeIsSet`, entity `hasBooking`, and coverage is `none` or `partial` per the linked-bookings data, or `hasBookedCourt === false` with no linked booking | *Court not booked yet* / *Court partly booked* | **See bookings** (scrolls to `GameLinkedBookingsSection`) — read-only, never opens a provider |
| `attendance` | attendance enabled (existing `attendanceEnabled` in the shell) and confirmed < PLAYING | *{c} of {n} confirmed* | **Nudge** (existing handler + cooldown caption, e.g. *Nudge again in 5 h*) |
| `cost` | cost card present and any share unpaid (PRD 348 states other than SETTLED/MARKED_PAID for all) | *{u} haven't paid* | **Settle** (opens `CostSettleSheet`) |

- Before the game (`resultsStatus === 'NONE'`): order seats → booking → attendance → cost.
- After FINAL: only `cost`. Seats, booking and attendance hints are never shown once results exist.
- Weather is not a hint; `WeatherRiskBanner` already carries its own action.

### What moves, what stays
- **Moves into the block** (no longer rendered separately for organizers): `AttendanceOrganizerStrip` (the strip's progress pill and Nudge become the `attendance` row; `AttendanceCard` keeps the participant-facing confirm controls and legend), and the open-spot summary row of `SpotOpenedGameSection` (the `GameQueuePanel` stays, and the participant-facing `SeatedFromQueueBanner` and `OpenSpotRow` for non-organizers stay).
- **Stays unchanged**: `GameLinkedBookingsSection` and its coverage badge, `GameCostCard` and `CostStateChip`, `WeatherRiskBanner`, `ParticipantSetupTags` (format tags, not hints), `GameParticipants`.
- With the flag off (see below) the moved surfaces render exactly as today.

### Accessibility and locales
- The block is a `region` labelled "Next steps"; each row's button has the full sentence as `aria-describedby`. Plurals for players/waiting/confirmed/unpaid in 11 locales; RTL checked.

## Implementation Decisions

- New feature folder `Frontend/src/features/organizer-next-actions/`: `buildOrganizerNextActions.ts` (pure: `(input) → Hint[]` where `input` carries `game`, `participants`, `viewerRole`, `attendanceSummary`, `bookingCoverage`, `costSummary`, `now`), `OrganizerNextActions.tsx` (presentational, receives hints and handlers), tests, and a `scrollToSection(id)` helper that reuses the existing section anchors (add `id`s to the queue panel and bookings section if missing).
- Inputs come from hooks already used by the shell: participants from the detail payload, `useGameAttendance` summary, the linked-bookings query result (coverage is already computed for the badge; export that helper), the cost card's data hook. No new endpoint, no schema.
- Permissions: `canEdit` (owner/admin) for the full block; `canInviteToGame && !canEdit` → seats row only with Invite.
- Rollout: `PlatformSetting` key `game.organizerNextActions.enabled`, read through the public flags endpoint from PRD 363 (dependency). Flag off → block hidden and the two moved surfaces render as today. Ship with the flag off, enable per environment.
- Nudge cooldown, attendance PATCH, cost sheet and queue panel are the existing implementations; the block only calls their handlers.

## Testing Decisions

- Unit matrix for `buildOrganizerNextActions`: 0/1/2 seats open × queue 0/2 × coverage full/partial/none × attendance 4/4, 2/4, disabled × cost settled/unpaid × role owner/admin/inviter/participant × resultsStatus NONE/IN_PROGRESS/FINAL. Asserts order, cap of two visible, FINAL shows cost only, participant gets nothing.
- Component: block hidden with zero hints; +1 more expands; buttons call the right handlers; flag off renders legacy strip and open-spot row (snapshot both states).
- Shell integration test: the attendance strip is not rendered twice in either flag state.
- UI test plan rows: organizer on a 3/4 game with a queue; partly booked game; within 24 h with unconfirmed players; FINAL with unpaid shares; participant view unchanged.

## Out of Scope

- Any provider call or booking change (plan §5.7 parked).
- Rescheduling (plan §5.6).
- A Home or card-level summary.
- New attendance, seat or cost logic.

## Further Notes

The dependency on PRD 363's flags endpoint is intentional so that this and the count share one mechanism. If 363 slips, ship the endpoint with this PRD instead.
