# PRD 360 report — Novices welcome (organizer toggle, tag, filter)

Implemented 2026-09-22. One boolean column, one named migration, eight surfaces. No notification, no rating effect, no subscription field, no new request.

## 1. Done

### Schema

- `Backend/prisma/schema.prisma` — `Game.suitableForNovices Boolean @default(false)` with a `///` comment stating what it is *not* (a level gate).
- `Backend/prisma/migrations/20260922100000_prd360_suitable_for_novices/migration.sql` — one `ADD COLUMN`, no backfill: an existing game stays untagged until its organizer says otherwise.

`prisma migrate dev` could not be used: two migrations from July 2026 (`…_add_padeloo_integration_type`, `…_add_klikteren_integration_type`) were edited after they were applied, so `migrate dev` insists on resetting the dev database. ### Shared

- `Frontend/shared/entityCapabilities.ts` — new capability `hasNoviceTag`: true for GAME, TOURNAMENT, TRAINING, BAR; false for LEAGUE, LEAGUE_SEASON, EVENT. `LEAGUE_CAPS` spreads `GAME_CAPS`, so it needed the explicit override — that spread is exactly how a league fixture would have silently inherited the promise.

## 2. Deviations from the PRD (with reasons)

- **Copy is "Novices welcome", not the plan's "Suitable for novices" / "Novice-friendly".** The PRD text is newer than plan §5.9 and says so explicitly; I followed the PRD. The column keeps the plan's name, `suitableForNovices`.
- **Pill tint is teal, not the private tag's purple.** The PRD says "same pill height and ring style as the private tag" — height and shape match exactly; reusing purple would have made a welcoming promise look identical to "Private" in the same row. Teal is also clear of the emerald "Playing" badge and the green results pill.
- **The hint stays visible while the switch is on, even with hints hidden.** The PRD only specifies the hint text. The one thing this tag must never be mistaken for is a change to the level gate, and the notes button is off by default for many organizers.
- **`update.service.ts` also drops the key for non-capable entity types.** The PRD only listed the whitelist entry; without this a `PUT` could tag a league fixture the create path refuses to tag.
- **`inboxInviteGameSelect` added.** Not in the PRD's projection list, but invite cards are `GameCard`s and would otherwise be the one surface missing the tag.
- **CONTRACT §0.1/§0.3** (no heavy commands, stay in your file list) did not apply: this ran as a single session, so tests, lint, typecheck, the shared build and the migration were run here through the serialized `./scripts/run-heavy`, and docs were merged directly — the precedent set by the PRD 358 and 359 reports. Two `package.json` test-script lines added for the same reason.

## 3. Known gaps

- **The create-payload link is pinned by a source-level assertion**, not a rendered test: `CreateGame.tsx` is a ~2 200-line component with no seam to render in a unit test. The assertion breaks loudly if the wiring is renamed or removed, but it is not a behavioural test. Same technique the Find card contract already uses on the backend for `socket.service.ts`.
- **No integration test for the create/update gate against a real database.** The rule is enforced in both services and unit-pinned; the DB-level proof would need the `*.integration.test.ts` harness and a seeded league fixture.
- **The Chats row does not repaint on a live flag change** — `ChatListGameCard`'s memo comparator does not look at this field. Pre-existing behaviour for that list (PRD 359 recorded the same for queue position); the tag updates on the next fetch.
- **Migration history drift is untouched** (see §1). It will block the next `prisma migrate dev` for whoever runs it.
