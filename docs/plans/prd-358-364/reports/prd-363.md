# PRD 363 report — Find recovery actions and looking-to-play count

Implemented 2026-09-22. No schema change. One new authenticated endpoint, one platform-setting switch, one empty-state component, one hint-line change on the Find strip. Built in the same working tree as PRDs 361, 362 and 364; the overlaps are listed in §4.

## 1. Done

### Backend

- `Backend/src/services/playIntent/playIntentLookingCount.ts` — pure: cache key per `(city, sport, sorted window)`, viewer exclusion on a distinct set, defensive parse of the cached payload.
- `Backend/src/services/playIntent/playIntentLookingCount.service.ts` — `PlayIntentLookingCountService.getForViewer(viewer, cityId, sport, now)`. The predicate is the pool's discovery predicate minus the per-viewer parts: GAME intents in `OPEN | MATCHED`, not expired, not consumed by a seat, a date key inside `playIntentDiscoveryDateKeys(city.timezone)`, still reachable (`intentWindowIsReachable`), owner not already PLAYING that day (`PlayIntentMatchService.usersBusyPlaying`, the same rule the pool uses for `inGame`). Reads intents only. The **user-id list** is cached 60 s (Redis when `REDIS_URL` is set, else an in-process `TtlCache`) and the viewer is subtracted after the cache, so one cached list serves every viewer. `count: null` while the flag is off.
- `GET /play-intents/count?cityId&sport` → `{ count, dayKeys }` in `playIntent.controller.ts` / `playIntent.routes.ts`, `authenticate`, `playIntentOptionalScopeQuerySchema`, scope defaults exactly like `/pool`.
- Flag: `PLATFORM_SETTING_KEYS.FIND_LOOKING_COUNT_ENABLED`, read through `getBooleanSetting`. The public flags endpoint (`GET /public/platform-flags`, `platformFlags.service.ts`) was written by the PRD 364 session minutes before this one reached it; this PRD's key is already in its allow-list and the endpoint is reused as-is.
- Admin: a "Find: Looking-to-play Count" card on Platform Settings (`Admin/index.html`, `Admin/platform-settings.js`), same On/Off select pattern as PRD 364's card.

## 3. Deviations from the PRD text, and why

- **Setting key names.** The PRD writes `find.lookingCount.enabled`; the admin write route validates keys against `PLATFORM_SETTING_KEY_PATTERN` (`^[A-Z][A-Z0-9_]{1,63}$`), so a dotted key could never be set. The key is `FIND_LOOKING_COUNT_ENABLED` (and `GAME_ORGANIZER_NEXT_ACTIONS_ENABLED` for 364); the flags response is keyed the same way.
- **Strip caption.** The PRD adds a caption line under the strip's text. The idle card already carried a count ("{n} players want to play today", from the pool, from one person up), so a second line would have put two numbers — from two different queries — on one card. While the flag is on, the idle card's hint line *is* the PRD's caption (same threshold, same source, tap opens the editor); while the flag is off, the existing hint is untouched. The Looking strip (viewer already looking) keeps its own "also looking nearby" count, which is a different, per-request number; adding the city-wide one beside it would have been confusing.
- **Lobby deep link.** The PRD suggests `navigationService.navigateToFind({ playIntentOpen: 1 })`. That param is only claimed by the My-tab provider (`acceptSharedDeepLinks`), so on Find it would have done nothing. Instead the Find provider now wraps the whole tab body and the empty state calls `openCompose` / `openLobby` directly — the sheet opens in place, no navigation.
- **"Clears any PRD 358 shortcut."** As shipped, a shortcut is the selected day (the row reflects the calendar; the only stored bit is the Weekend pin). "Clear filters" keeps the day and view, so the highlight stays — clearing it would have moved the day, which the PRD also forbids.
- **Sport prefill.** Create receives Find's resolved sport (`findLevelSport`) as well as the date. Without it, a player browsing Tennis would land in a Padel draft.
- **Never a past day.** Not in the PRD: an empty *past* calendar day offers today, not a game in the past.
