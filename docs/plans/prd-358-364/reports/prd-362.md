## 2. Deviations from the PRD (with reasons)

- **TRAINING trainer also sees the button.** The PRD gates on `isPlaying`; a trainer is NON_PLAYING by construction, so the coach would never have had the one action they want after a session. The trainer's draft opens with "I'm not playing" on (creator becomes `trainerId` on the backend) and invites the players only.
- **Trainer invite is a real trainer invite.** The PRD's "trainer step" does not exist in create; what exists is `invitesApi.send({ asTrainer })` (the invite modal uses it). The previous trainer is appended to the invitee rows and sent with `asTrainer` unless the creator has taken the trainer role.
- **No post-create "Make it weekly" toast link.** The PRD asks for one only if the existing entry needs it; the Repeat row (PRD 345) is already inside the create flow and the created game's settings has "Make this a weekly game". A third path would break plan §2 rule 11.
- **Invitee users travel with the draft** (`invitedPlayers`), not only ids. Without it the existing chip effect drops anyone missing from the Browse-city players list while still inviting them, which violates user story 3.
- **A context banner was added to the rematch draft.** Not in the PRD; it exists because the form opens with everything set except the time, and a one-line "why" beats a silent empty slot. It is not a nudge (user-initiated, not dismissible) and renders only for `rematchOf`.
- **`createdFromGameId` analytics: not sent.** No such field exists on `Game` (`sourceGameId` in the schema belongs to `UserAchievement`); the PRD forbids adding a column here.
- **CONTRACT §0.1/§0.3** (no heavy commands, ownership list) did not apply: single session, so tests/lint/typecheck ran here through `./scripts/run-heavy`, and docs were merged directly — same as the 358–360 reports.

## 3. Known gaps

- **`CreateGame` / `GameDetailsShell` are pinned by source assertions**, not rendered tests (no seam in either 2 000-line component). The e2e spec is the behavioural proof (passed locally).
- **A club with exactly one court shows that court preselected in the draft.** That is the create flow's own single-court default (`CreateGame.tsx`, `sportCourts.length === 1`), not carry-over: the rematch draft carries no `courtId` / `gameCourts` (asserted). Worth knowing when reading GD-RM-05.
- ~~Trainer row has no "Trainer" badge~~ — closed in review: `ParticipantsSection` takes `trainerInviteId` and the trainer invitee's row carries an amber **Trainer** pill (`playerCard.isTrainer`, lucide `GraduationCap`); hidden once the creator takes the trainer role. Test: `ParticipantsSection.trainerBadge.test.tsx`.
- ~~Blocked users are not filtered client-side~~ — closed in review: the create flow's invitee effect loads `GET /blocked-users` alongside the players store and drops blocked ids from both the rows and `invitedPlayerIds` before anything renders, so a blocked co-player is never shown nor sent an invite. The endpoint's own check remains the last line.
- **The invite loop is sequential and best-effort** (pre-existing): if one invite fails, later ones still go out and no per-recipient error is surfaced.
