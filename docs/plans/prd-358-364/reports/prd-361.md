# PRD 361 report — Played with: recent co-players as the invite Search zero-query state

Implemented 2026-09-22. No schema, no notification, no new route, no new tab. One backend module holds the co-play predicate; the invite modal groups its zero-query list under two headings.

## 1. Done

### Backend

- `Backend/src/services/user/coPlay.service.ts` (new) — the single home of the predicate: `loadCoPlayers(viewerId)` (both PLAYING, `resultsStatus = FINAL`, `startTime` inside `CO_PLAY_WINDOW_MONTHS = 12`, entity type not BAR / LEAGUE_SEASON / EVENT; returns `gamesTogetherCount` and `MAX(startTime)` as `lastPlayedTogetherAt`, ordered by recency), `loadBlockedUserIds(viewerId)` (both directions), `pickTopCoPlayerIds` and the pure `rankInvitablePlayers` (`lastPlayedTogetherAt DESC NULLS LAST, gamesTogetherCount DESC, interactionCount DESC`, stable).
- `Backend/src/controllers/user/social.controller.ts` — `getInvitablePlayers` now: uses the module instead of the inline SQL; adds blocked users (either direction) to the exclusion set; decorates every row with `lastPlayedTogetherAt` (ISO or null) next to `gamesTogetherCount`; loads the ten most recent still-invitable co-players by id when they are not already in the Browse-city page (so a regular who moved is still "played with"); orders the empty-query response with `rankInvitablePlayers` and keeps the interaction order for name searches. Nearby-city expansion is untouched.

**Index check (PRD asked):** `EXPLAIN (ANALYZE, BUFFERS)` on `padelpulse_dev` for the player with the most PLAYING seats (258) runs the query in ~31 ms and already uses an index-only scan on the existing `idx_GameParticipant_userId_gameId_status` (userId, gameId, status) plus `GameParticipant_gameId_attendance_idx` for the partner side. `@@index([userId, status])` was **not** added: it would duplicate the existing composite.

## 2. Deviations from the PRD (with reasons)

- **The block filter did not exist.** The PRD says "existing block filter in the handler"; `getInvitablePlayers` had none. Added via `loadBlockedUserIds` (both directions) into the exclusion set, so blocked users never appear anywhere in the picker, not only in Played with.
- **BAR stays excluded** alongside LEAGUE_SEASON and EVENT. It was already excluded and can never reach FINAL (`hasResults: false`); keeping it explicit means a future BAR scoring change cannot widen the list silently. Same effective predicate as the PRD.
- **Caption replaces the "N together" badge on Played-with rows** instead of sitting next to it: both carry the same count, and two renderings of one fact is a defect under plan §2 rule 11. Rows outside the group keep the badge.
- **Everyone never repeats a Played-with row.** The PRD text only says "the existing list"; a duplicated person with one checkbox state in two places would confuse selection.
- **Cache is a per-open react-query bundle, not a store cache.** The modal was not on react-query; wrapping the existing load in `fetchQuery` with a per-open nonce gives the PRD's "no refetch on clear" and keeps each new open fresh (no stale roster after sending invites).
- **CONTRACT §0.1/§0.3** did not apply: single session, so tests, lint, typecheck and the EXPLAIN were run here through `./scripts/run-heavy`, and docs merged directly — the precedent of the 358–360 reports. Two `package.json` script lines added for the same reason.

## 3. Known gaps

- **Headings are not sticky** inside the virtualized list (rows ≥ 30). They scroll with the list; a sticky variant would need a second positioning layer in `PlayerInviteVirtualList`.
- **Relative time is not live.** The caption uses the render-time distance ("3 days ago"); a modal left open across midnight keeps the old wording until the next render.
- **No DB-level test for the away-city name search filter across nearby expansion**; the nearby path is unchanged and covered by its existing cases.
